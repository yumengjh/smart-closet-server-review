# 图生图 HTTP 504 排查记录

## 已确认的现象 · 2026-09-28

- 服务商为 api.yumg.cn，图生图使用 OpenAI Images 的 `/v1/images/edits`。
- 历史四次图生图失败耗时：60.26、60.25、60.47、60.11 秒，均收到服务商 HTTP 504。
- 本机配置等待上限 180 秒，失败代码为 `PROVIDER_HTTP_504`，不是本机超时 `PROVIDER_TIMEOUT`。
- 最近两次输入分别为校正照片、预抠图，均约 60 秒失败；输入约 5 MB，1440×1920。尚无证据证明图片尺寸或预抠图导致失败。
- 同一个 flare 模型此前文生图约 37 秒成功，但不能据此推断图生图路径正常。
- 用户随后确认原因是云端 Nginx 超时时间太短，已调整为 200 秒（用户提供的结论，未直接读取云端配置）。本机对应服务商等待上限已从 180 秒调整为 240 秒。此次修正提示词未再调用付费生图、未重传用户图片。

脱敏时序记录见 [edit-timeouts.json](../reports/generation/edit-timeouts.json)。

## 云端优先检查

1. 按上述时间和 `/v1/images/edits` 路径关联访问日志、错误日志和 API 网关的上游请求日志，确认哪一层生成了 504。
2. 若使用 Nginx，检查真正匹配 `/v1/images/edits` 的 location 中 `proxy_read_timeout`，以及是否有更内层配置覆盖。其默认值为 60 秒，表示相邻两次读取之间的空闲超时，并非整个请求的总时长。
3. 检查 API 网关自身访问模型上游的 HTTP 超时、部署平台/负载均衡的超时，以及图生图对应的上游路由和账号可用性。
4. 如果上游生成确实需要超过 60 秒，协调各层允许的等待时间。外层链路依然较短时，只调大其中一层不会生效。当前本机 240 秒为整个请求的等待上限；Nginx 的读取空闲超时与总时长含义不同。
5. 调整后先做一次可追踪的图生图测试，对照返回时间和云端日志。超时不保证上游已取消，也不能保证未计费，避免连续重复提交。

用户已确认并修复 Nginx 超时。随后保存的任务 a01ae01c-7abf-4843-b443-63d002266b80 中，flare 图生图约 58.20 秒成功；其后因透明检查发现主体触及画布边缘而进入 NEEDS_REVIEW。图生图成功不代表衣物内容一致，用户发现生成图重绘了衣物细节，需要另行修正编辑目标。

## 本机已修复

- 504 明确提示网关等待上游超时，避免误导去检查余额。
- 429、认证失败、参数错误等分别提供对应提示，不泄露上游响应原文或密钥。
- 客户端等待超时与连接超时使用独立错误代码，避免被错误归类为普通连接失败。
- 页面按错误代码解释历史任务；保留原始任务记录。刷新页面后，旧 504 任务也会显示准确解释。
- 页面资源增加版本参数。若仍使用旧预设或自定义步骤，刷新页面并检查自定义 JSON；普通预设现在包含 ENSURE_TRANSPARENCY 和可选前置抠图。

规范来源：[HTTP 504 定义](https://www.rfc-editor.org/rfc/rfc9110.html#name-504-gateway-timeout)、[Nginx proxy_read_timeout](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout)。
