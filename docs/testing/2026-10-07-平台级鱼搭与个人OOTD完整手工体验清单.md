# 鱼搭平台级助手、基准人物与 OOTD 完整手工体验清单

日期：2026-10-07。测试地址：[localhost:8080](http://localhost:8080)。

这份清单对照最初完整设计的12章、2026-10-07全身／半身照与AI启用补充，以及人物提交反馈修复编制，共 **299 个编号验收点**。它列的是应检查的行为，**空白项不代表已通过，既有测试报告也不代替你的体验结果**。页面找不到按钮、信息或入口，同样记为问题，不用反复搜索。

## 怎么使用

1. 先记录浏览器、页面地址、账号与当前图像额度；创建可丢弃测试衣物／搭配，用于修改和删除。不要为测试清空自己的真实资料、记忆或默认人物；临时改资料前记下原值，完成后恢复。
2. 先做A–F、I和其他免费项；使用已有结果完成G、H、J、K的查看／管理项。最后由你选择是否执行标注“图像／识图”的测试。
3. 每项勾选表示已执行，并在“结果”填：通过、失败、找不到入口、不适用或未测。未满足样本前提就填不适用并说明，不按通过计算。
4. 多个质量检查可以复用同一次生成。例如一张有照片人物可覆盖G10–G14；一张上下装OOTD可覆盖H14–H18、H20–H24等。不要为每行都重新生图，也不要为了测试额度不足用完额度。
5. 常规页面与规则检查不应调用识图／生图。“聊天”仍会使用聊天模型／聊天额度；“图像”是实际生图，人物和OOTD当前每次单张使用1个图像额度；“识图”按原有模型和额度策略。关闭页面／取消不能保证已派发请求退款。
6. A–L是本轮体验主体；M明确当前限制或设计缺项；N保留全部天气后续体验点；Q交由工程隔离验证，不要求你重启服务、破坏图片、伪造接口或故意制造数据库故障。

**建议先完成的主链路：** A01–A12 → B01–B10 → C01–C08 → D01–D06 → E01–E19 → F01–F13 → G01–G14、G17 → H01–H20 → I01–I20 → J01–J06 → K01–K12。其余编号用于边界体验，仍应记录是否测过。

当前沿用yumg上游；人物与OOTD已启用已验证的gpt-image-2.5-flare。人物最多1张可选照片；OOTD最多5张参考，**包含1张人物，所以通常最多4件独立衣物**。帽子、首饰等也可能占一件参考，超过限制应明确拦截。

真实天气、城市选择、天气排序与通用联网尚未开放。人物提交编号仅在当前页面保留，刷新后只能查已有任务，尚无跨刷新原编号恢复。原照、人物、OOTD现有页面独立删除，没有一键关联清除按钮。OOTD列表的来源／版本追溯展示也要按原设计核对，缺少就记缺项。

## 测试样本准备（缺少时可标不适用）

- 测试衣物：上衣、裤子、半身裙、连衣裙、两件不同外套、鞋；按实际库存补帽子、眼镜、不同位置首饰及未知品类物品。多季／未知季节、假两件、复合图案样本用已有资料即可，不必重新识别。
- 组合：一套上下装、一套连衣裙无鞋、一套单外套、一套双外套冲突、并排两套。可以复用同一测试画板逐步调整并保存。
- 可选照片：本人全身、带脸半身的JPG／PNG；先选择预览，只有你明确生成才上传。无照片默认值测试只看确认预览即可。
- 并发与账号：两个标签页；有条件时另一账号、手机或同账号第二台设备。另一设备不能用它自己的localhost访问本机服务，应使用运行服务电脑的局域网地址。
- 已有结果：已确认人物和至少一张OOTD，可覆盖持久化、反馈和删除；缺少时由你决定是否生成。删除只用你愿意丢弃的测试素材。

## 反馈文档怎么写

请使用单独的《鱼搭逐项体验反馈模板.md》，或在本清单的“结果”栏直接填。

失败时保留：编号、测试时间、页面、原始问题、实际步骤、预期结果、实际结果、是否能复现、截图／任务编号。**先记录首次失败，不需要不断换问法或不断重新生成来证明它能成功。**

分类建议：阻断（无法继续／错改／越权／重复扣费／删除复活）、主要问题（错误统计／不合理穿搭／缺入口）、体验问题（反馈、布局、速度、文案）、建议。图片质量可单独评价人物相似度、衣物保真、数量与层次、基础服饰残留、鞋和配饰、身体异常。

不要在反馈里贴密码、Cookie、CSRF令牌、上游密钥或完整私人输入载荷。任务编号、日期、错误文字和必要截图通常足够定位；照片按你愿意提供的范围提交。
