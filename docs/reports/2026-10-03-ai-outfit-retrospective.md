# AI 衣柜智能搭配问题复盘：从执行可观测到源头候选筛选

日期：2026-10-03
范围：`smart-closet-server` 后端、`agent-runtime`、相邻 `smart-closet` 前端。
文档状态：实现与验收已完成，本次改动准备提交；未自动批量重识别历史衣物。

## 1. 本次解决了什么

这次工作起于用户反复遇到明显的搭配错误：两件外搭一起推荐、衬衫与连衣裙混为主体，以及画布中外套遮住内搭、层次看起来不正确。用户希望判断问题来自工具、元信息还是提示词，并要求在前端展示足够详细的决策与执行信息。

最终交付包括四部分：

1. 每条助手回复增加持久化的「决策与执行记录」，可以核对实际模型输入、工具调用、选衣校验和画布变化。
2. 继续使用后端结构规则，阻止重复穿着位置、连衣裙与上/下装冲突、不完整主体，以及没有已核对资料支撑的自动叠穿。
3. 拼贴整理将主体与外搭分开展示，减少不透明外套图片覆盖衬衫的问题。
4. 从源头补充穿着资料，改成「后端预筛选合法候选 → AI 选择与解释 → 执行前再次核验」，减少选错后拒绝重试的调用。

本次没有完成真实尺寸或人体适配模型，也不能保证配色、通勤场景和审美质量全面改善。新增视觉建议尚未用付费真实照片识别做质量对比。

## 2. 问题背景与最初判断

用户提供的典型结果是「蓝灰格纹短袖衬衫＋黑色长裤＋深灰夹克」。截图中还有衬衫与粉色西装外套的组合。这里必须分别判断三个问题：

| 问题 | 需要的证据 | 不足以得出的结论 |
| --- | --- | --- |
| 穿着结构冲突 | 衣物有效品类、角色数量、主体是否完整 | 模型说“适合通勤”不能证明结构合法 |
| 具体单品可否叠穿 | 穿着用途、版型、厚薄与来源；进一步需要实际尺寸适配 | 不能因为叫“衬衫”和“夹克”就认定一定兼容或一定互斥 |
| 拼贴图片遮挡或错层 | 布局前后坐标、尺寸、图层、浏览器执行回执 | 拼贴遮挡不等于真实穿着方式；旧截图不能证明偏移来自哪一步 |

原有 `daily-structure-v1` 已约束基本角色和数量，但允许 `TOP + BOTTOM + OUTER`。衣物元信息包含颜色、风格、季节、领型、袖长和表面纹理等，却没有穿着用途、版型与厚薄字段。模型对具体叠穿的判断因此缺少资料和明确的前置约束。

提示词虽然要求不要无依据推断，实际模型仍可能提交带外搭的组合。后端最终拒绝只是防线；如果拒绝后再调用模型修正，就会增加时间和 token。

## 3. 工作顺序与阶段演进

| 阶段 | 做法 | 作用及局限 |
| --- | --- | --- |
| 前置工作区提交 | 根据实际改动提交已有角色、结构、证据和布局修复 | 保存本轮开始前的基线，避免混淆旧改动与新实现 |
| 决策记录建设 | 保存实际输入、返回、工具和画布证据 | 先让问题可定位，不在缺少证据时随意改搭配策略 |
| 保守保护 | 资料不足时拒绝主体与外搭自动组合 | 阻止错误落地，但仍可能产生拒绝后的模型重试 |
| 拼贴展示修复 | 整理时主体在左、外搭在右 | 修复图片遮挡，不宣称实现虚拟试衣 |
| 源头改造 | 识别新字段、用户核对、后端候选池、模型选候选 ID | 将结构和保守叠穿筛选移到模型选择之前 |

前置提交为后端 `daf398c` 与前端 `6a6e51e`。它们属于已有改动的保存，不是后续候选池功能的提交。本文之后的改动是本次待提交内容。

阶段报告保留了当时的规则与验收结果。最终状态以本文和源头修复报告为准，不能把中间阶段“所有外搭暂不推荐”误解为永久策略。

## 4. 决策与执行记录如何实现

### 4.1 后端持久化及关联

新增迁移 `V10__agent_trace.sql`：

| 数据 | 用途 |
| --- | --- |
| `agent_message.request_id` | 将助手回复与运行关联 |
| `agent_trace_run` | 保存运行所属会话、状态、序号和开始时间 |
| `agent_trace_event` | 保存有序事件摘要和详细脱敏快照 |
| `agent_trace_board` | 将生成/编辑的临时画板与运行关联 |
| `agent_trace_client_event` | 按会话和事件 ID 去重客户端补传 |

`AgentTraceService` 负责序号分配、事务写入、所有权验证、摘要分页、详情读取、画板关联和客户端事件处理。记录跟随会话保存；会话删除时级联删除记录。详情不会全部塞进普通聊天正文。

运行开始即保存 `RUNNING` 助手回复占位。重启时将未完成运行标记为中断、回复标记失败，保留已记录证据并清理活动运行状态，不自动重试。这样中途崩溃也不会让记录失去入口。

### 4.2 实际记录的内容

`agent-runtime/src/graph.ts` 在每次模型调用前后，通过本轮鉴权回调提交记录：

- 实际模型、推理配置、提示词版本及哈希。
- 实际消息、上下文、偏好和公开工具定义。
- 模型返回的公开文字、工具调用 ID、参数、耗时及 usage。
- 流式异常类型、消息、已返回的部分内容。

`AgentService` 记录真实业务工具的开始、结果、拒绝原因与耗时；校验记录保留候选、角色数量、衣物版本、有效值、来源和规则版本。运行结束记录总耗时、usage 和业务工具次数。

这些记录不会再进入模型对话历史，也不会为了生成“决策解释”额外调用模型。记录的是公开理由和执行证据，不是隐藏思维链。

### 4.3 脱敏与权限边界

记录前递归处理敏感字段及本轮已知秘密，隐藏 API 密钥、回调凭证、认证信息、图片数据和个人身体资料。画布快照按字段白名单保留 ID、角色、版本、坐标、尺寸、旋转、图层、裁剪等，不保留图片 URL 或 base64。

读取和补传接口都检查账号、会话及运行关联；不能跨账号读取记录。客户端上传不能作为“真实穿着正确”的证明，因此与服务器接受的回执分开标注。

脱敏实现覆盖当前明确的数据结构和已知敏感值，仍需要在新增字段时继续维护。不能将这项实现理解为对任意自由文本的完全匿名化保证。

### 4.4 前端入口及画布后续变化

`AssistantPanel.vue` 为每条助手回复增加记录入口；`AgentTraceModal.vue` 使用 Ant Design Vue 大模态框，按四类展示：输入与上下文、选衣与校验、工具调用、画布变化。

摘要分页读取，详情点击后加载；按序号合并实时记录。旧回复没有记录时明确显示「当时未记录」，不会根据现有数据补造历史。

新临时搭台生成/编辑记录指令、执行报告、ACK、前后版本和画布快照。后续手动拖动、变换、角色/图层修改、整理、撤销、重做和本机恢复分别记录来源。同一画板可以关联多个运行，让较早生成记录也能追踪后续编辑。

客户端采用按账号隔离的本机队列；离线或上传失败时保留，在线恢复后补传。事件 UUID 去重，避免重复上传造成重复记录。存储不足时暂留内存并提示用户。

旧版预览建议在独立草稿上的确认/保存流程，尚没有与新临时搭台同等完整的后续画布日志；其模型输入、工具参数和校验仍可查。

## 6. 保守规则与拼贴展示修复

用户明确选择「资料不足就不自动叠穿」。中间版本 `daily-single-layer-v2` 因此暂不自动推荐主体与外搭组合，后端校验、自动编辑和预览接受复用同一规则；手动编辑继续开放。

真实请求 `885254e9-22be-48fa-848e-fd4fc7be14f2` 中，模型第一次仍提交带外套的方案，后端拒绝后，模型重新提交成功：衬衫加裤子、另一件衬衫加裤子，以及单件连衣裙。回复说明外套兼容性未验证。

这证实了后端防线有效，也暴露了用户指出的成本问题：模型仍先选错，然后付费再修正。

布局方面，`outfit-layout.ts` 保留角色层级约束，但不再用不透明外套贴纸模拟覆盖主体的试衣效果。整理时主体放左侧、外搭放右侧，等比例缩放并限制在画板内；单层主体仍居中。

该布局不会自动修改已有画板；需要点击「整理穿搭」才应用。Ego 手动添加深灰夹克后验证衬衫完整可见，验收结束恢复生成结果，没有保存到搭配库。

## 7. 源头资料升级：garment-v4

在原有单次识别调用中加入：

| 字段 | 内容 | 来源约束 |
| --- | --- | --- |
| `fit` | 修身、合体、宽松、廓形等版型建议 | 照片只能提供建议，有参照才推断 |
| `thickness` | 薄、常规、厚等厚薄线索 | 不能从品类、颜色、季节或表面纹理直接猜真实厚度 |
| `wearingModes` | 可作内搭、可作外搭、适合单穿 | 单品用途建议不等于与另一件兼容 |

三个字段的自动有值状态为 `INFERRED`；无法判断时保留未知、不适用或冲突。它们不是 `OBSERVED` 实物事实。

旧 JSON 结果缺少新字段时，`GarmentRepository` 返回空值，不触发空指针，不覆盖旧元信息。前端保留空值和来源说明。用户可以手动补齐，也可以在核对实物后点击核对按钮，再保存为用户覆盖值；即使输入与自动建议相同，也能确认来源。恢复自动值会撤回待保存的确认。

搭配查询不会启动识别。历史衣物未自动批量补全；已有「重新识别信息」仍需用户主动操作，可能产生识别费用。本次实现了字段兼容、手动补充和核对入口，没有完成按缺失字段运行的独立 AI 批量补全任务。

## 8. 候选池如何把约束移到模型之前

新增 `OutfitCandidates` 与工具 `get_outfit_candidates`：

1. 后端按账号读取已入柜库存，扫描上限 1000 件，返回截断状态。
2. 按有效品类确定角色，构造连体主体或上装加下装。
3. 合入用户明确指定的必选衣物。
4. 尝试附加鞋、包或外搭，先执行结构和保守叠穿规则。
5. 去重并返回最多 40 个合法候选，为候选生成本轮有效 ID。
6. 衣物资料去重返回，不在每个候选里重复完整元信息。
7. AI 根据场景、颜色、风格等选择候选 ID，填写名称和理由。
8. 服务端解析候选 ID，执行前重新检查衣物所有权、状态和当前元信息，再交给临时搭台执行。

运行时公开的新建搭配工具 schema 使用 `candidateId`，不再让模型自由传入任意 `garmentIds`。候选只在当前运行有效，重新获取会替换候选池，结束后清理。已取得候选池的运行不能绕回任意 ID 拼接。

兼容旧内部调用的处理路径仍存在；因此不能表述为后台所有入口彻底移除了 `garmentIds`。面向模型的新建工具已改为候选 ID，执行前校验仍保留。

候选中的质量信息只传精简的来源和状态，完整依据可以按需查询单件衣物；实际选中衣物的完整资料仍进入校验记录。这样减少重复证据占用模型上下文。

### 8.1 最终保守叠穿资格

`daily-evidence-v3` 在既有结构规则之上，要求内外两件同时满足：

- 版型、厚薄、穿着用途三项均有用户覆盖值，并且非空。
- 内件标记可作内搭，版型为修身或合体，厚薄为薄或常规。
- 外件标记可作外搭，版型为宽松。
- 外件厚薄等级不小于内件。

这些是可解释的保守筛选条件，不是实际尺寸匹配或物理试穿证明。`wearingDataConfirmed` 表示资料已核对；`layeringVerified` 仍为 false，不将候选通过误说成真实叠穿已验证。

### 8.2 候选算法的范围

候选生成是确定性有限枚举，不额外调用模型，不做审美排名。最多 40 个结果不能覆盖所有合法组合；通常从主体出发附加一件鞋、包或外搭，不穷举全部可选配饰组合。库存较大时顺序和限额可能影响覆盖范围。

因此，未出现在候选中不代表衣柜没有该衣物。工具返回库存与资料缺失信息，提示词也要求区分候选范围与真实库存。需要定位指定单品时才额外查询衣柜。

## 9. 升级中发现并修复的费用保护问题

升级字段后，一项工作流回归失败：识别返回 HTTP 502，后续预设生图却执行成功。排查过程中单独验证了旧提交基线，确认不是可以直接忽略的已有失败。

原因是两处逻辑把“需要明确衣物目标”的协议写死为 `garment-v3`：

- `RecognitionService` 是否要求识别目标。
- `WorkflowService` 是否在目标缺失时停止预设生图。

升级为 v4 后，该保护条件不成立。修复为统一的 `RecognitionSchema.requiresTarget`，兼容旧 v3 和当前 v4，并增加版本回归测试。识别失败时再次验证后续预设生图被跳过。

按用户要求，发现该问题及定位后使用系统 `say` 播报，同时在聊天中说明；没有带着已知失败直接发布。

## 13. 经验与后续工作

本次最关键的变化，是把“模型可能会遵守”的提示词要求变成执行前可检查的候选边界。观察记录先帮助分清角色冲突、单品资料不足和拼贴遮挡，再用规则防止错误落地，最后把规则移到选择之前，减少拒绝后的付费重试。

源头资料也不能简单追求填满。照片建议、用户确认和真实试穿证明是不同等级；未知需要保留，不应为了恢复外搭功能伪造兼容结论。

后续优先项：

1. 用用户授权的真实照片验证新字段建议质量，比较识别前后结果和未知率。
2. 若需要旧衣物 AI 补全，先明确缺失字段、费用预算、缓存与增量合并规则，再提供独立任务；避免覆盖用户确认值。
3. 评估候选覆盖度与顺序偏差，为大衣柜增加可解释的筛选条件或分页。
4. 用相同库存、会话历史、请求和模型配置做成本/质量对照，持续统计拒绝率、模型调用、token 和用户修改率。
5. 补齐旧版独立预览草稿的后续日志及必要故障注入场景，单独处理已有前端间距测试失败。
