# 便携版一键启动设计

日期：2026-10-18 · 分支：`feat/portable-package` · 使用与运维说明：[docs/PORTABLE_PACKAGE.md](../PORTABLE_PACKAGE.md)

## 1. 背景

鱼搭要参赛。评委和试用者拿到作品时，通常没有 Docker、没有 Java 21 和 Node 22，也不会照着 README 下载五个模型文件、生成密钥、
配环境变量。现有的两种运行方式都不适合：

| 现有方式 | 对评委的门槛 |
| --- | --- |
| Docker Compose（`compose.yaml`） | 要装 Docker；要先跑脚本下载或导出模型（Chinese-CLIP 导出要 6 分钟、6 GB 临时磁盘）；要写 `.env` 里的密钥 |
| 源码运行（`scripts/start-with-agent.sh`） | 要装 JDK 21、Maven、Node 22；前端在另一个私有仓库，要先构建；只支持类 Unix shell |

所以需要一种“解压即用”的形态：一个压缩包，几百 MB 也可以接受（模型本身就有约 460 MB），里面一个启动文件，双击后有菜单，
能启动、停止、重启、检查环境、看本地模型的压力。

## 2. 目标与不做的事

目标：

1. **一键启动**：每个平台一个压缩包，解压后双击一个文件即可运行，不需要安装任何软件，不需要联网下载。
2. **自带全部依赖**：Java 运行时、Node、构建好的前端、服务端、Agent、全部本地模型。
3. **可控制的启动器**：交互菜单（启动、停止、重启、状态、日志、环境检查、模型压力评估、实时监控、设置、重置密码、备份、退出），
   同样的功能也能用命令行调用，方便脚本与 CI。
4. **主动提示**：启动进度、访问地址、管理员账号与初始密码（改过之前一直提示）、失败原因与日志。
5. **多平台**：Linux x64 / arm64、macOS Apple Silicon / Intel、Windows x64。
6. **全部在 GitHub Actions 完成**：构建、测试、查看结果、发布，不依赖任何人的本机。
7. **不污染系统**：所有运行时文件都在解压目录里，删除文件夹就是卸载。

不做：

- 不做 GraalVM 原生镜像（理由见 4.1）。
- 不做安装程序（.msi / .dmg / .deb）、自动更新、开机自启。
- 不做代码签名与苹果公证（需要付费证书；第 12 节列为后续）。
- 不改变容器部署：服务端新增的组件只在便携版设置的参数下启用。
- 不在首次启动时联网下载模型：项目约定“服务不得自动下载模型”，便携版同样遵守，模型直接放进压缩包。

## 3. 约束（来自现有项目）

| 约束 | 对设计的影响 |
| --- | --- |
| 服务端是 Spring Boot 4.1 + H2 文件数据库 | 不需要外部数据库，数据目录即全部状态；H2 文件锁要求离线操作（重置密码、备份）时服务必须已停止 |
| 图像处理依赖 JavaCPP/OpenCV 与 ONNX Runtime 的 JNI 本地库 | 本地库与操作系统、CPU 架构一一对应，必须按平台构建并在该平台实测 |
| `pom.xml` 已有 `native.platform` 属性按平台选 JavaCPP 分类器 | 直接复用，每个平台打一个只含本平台 OpenCV 的 jar |
| Agent 运行时是 Node（LangGraph），通过 `CLOSET_AGENT_SECRET` 与服务端互信 | 需要随包带 Node；密钥首启随机生成 |
| 前端在私有仓库 `yumengjh/smart-closet`，用 `npm run build:server` 发布进 `static` | CI 需要该仓库的读权限 |
| 模型来源：U²-Net 与 bge 向量从固定地址下载并校验；Chinese-CLIP 没有官方 ONNX，需要用 PyTorch 自行导出 | 模型准备放在单独作业里做一次，结果用缓存复用（与 `deploy.yml` 共用导出缓存） |
| 管理员通过 `CLOSET_BOOTSTRAP_USERNAME/PASSWORD` 创建，首次登录必须改密码；每个账号最多 5 个会话，超出挤掉最旧的 | 启动器生成初始密码；判断“是否已改密码”时要避免挤掉用户自己的会话（6.6） |
| 远程访问（含便携登录链接）要求 HTTPS，仅回环地址允许 HTTP | 默认只监听 127.0.0.1；局域网模式明确提示是 HTTP |

## 4. 方案选型

### 4.1 Java：裁剪运行时，而不是原生二进制

| 方案 | 体积 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| GraalVM native-image（真正的二进制） | 服务端约 150–250 MB，启动 < 1 秒 | ONNX Runtime、JavaCPP/OpenCV 是 JNI 库，需要逐个写 JNI 与资源配置；MyBatis-Plus、Flyway、H2、Spring Security 的反射与动态代理需要大量元数据；每次升级依赖都可能在运行时才报错；五个平台各要一台原生构建机，构建 10 分钟以上 | 不采用 |
| 完整 JRE（Temurin 21 JRE） | 约 130 MB | 带了用不到的模块 | 可行但浪费 |
| jpackage 生成 app-image | jlink 运行时 + 原生启动程序 | 原生启动程序只能启动 Java，我们还要同时管 Node 与菜单；macOS 上生成 .app 后反而更难给出终端菜单 | 不采用 |
| **jlink 裁剪运行时 + 按平台打包的 fat jar** | **53–65 MB** | 需要自己维护模块清单 | **采用** |

采用的模块：`java.se`（聚合全部 Java SE 模块，含 ImageIO 所需的 `java.desktop`、JDBC、JMX、XML）加
`jdk.unsupported`（许多库用 `sun.misc.Unsafe`）、`jdk.crypto.ec`、`jdk.crypto.cryptoki`（HTTPS 调 AI 服务）、`jdk.zipfs`、
`jdk.charsets`（Windows 上的 GBK 等编码）、`jdk.localedata`（只保留 en、zh）、`jdk.management`、`jdk.net`、`jdk.naming.dns`、
`jdk.security.auth`、`jdk.security.jgss`、`jdk.httpserver`、`jdk.jfr`。参数 `--strip-debug --no-man-pages --no-header-files
--compress=zip-6`。宁可多带几个模块：漏掉一个模块的代价是某条冷门路径在用户机器上 `ClassNotFoundException`。

启动仍是 `runtime/java/bin/java -jar app/server.jar`，与容器版行为完全一致，测试结论可以互相印证。

曾考虑用 AppCDS 加快启动，但 fat jar 里的类由 Spring Boot 自己的类加载器加载，CDS 收益很小，而且 CDS 归档会校验类路径，
解压到别的目录后会被静默禁用。实测启动已经只要 3–24 秒，放弃。

### 4.2 Node：携带官方可执行文件

| 方案 | 结论 |
| --- | --- |
| **官方 Node 24 可执行文件（不含 npm）+ Agent 的 dist 与生产依赖** | **采用**。Agent 生产依赖（LangChain.js、LangGraph.js、zod）全是纯 JS，一次构建通用于所有平台；同一份 Node 还用来运行启动器 |
| Node SEA（单文件应用） | 仍然要带完整 Node，体积不变，还要处理资源注入与签名 |
| esbuild 打成单个 JS | 能省掉 node_modules 的几千个小文件，但 LangChain 的动态导入有打包风险，而 Agent 的测试针对的是源码；收益不足以承担风险 |
| Bun 编译 | 引入第二套运行时，行为与容器版的 Node 不一致 |

Node 二进制直接取 `actions/setup-node` 在该平台 runner 上安装的官方构建（`process.execPath`），不需要自己拼下载地址。

### 4.3 启动器：Node 脚本 + 极薄的平台启动文件

| 方案 | 结论 |
| --- | --- |
| **Node 脚本（只用内置模块）** | **采用**。已经带了 Node，零额外体积；一份代码跑三个系统；与 Agent 同语言，团队熟悉 |
| Go 编译的原生程序 | 体验最好，但要多维护一种语言和一条交叉编译链 |
| shell + bat + PowerShell 各写一份 | 三份逻辑必然不一致，Windows 批处理处理 JSON、HTTP、进程都很吃力 |

平台启动文件只负责找到包内 Node 并运行 `app/launcher/yuda.mjs`：

| 平台 | 文件 | 额外动作 |
| --- | --- | --- |
| Windows | `start.bat` | `chcp 65001` 切换控制台为 UTF-8；双击运行出错时 `pause` 防止窗口一闪而过；文件内容只用 ASCII（cmd 在 chcp 之前就会按本地代码页读取批处理） |
| macOS | `start.command` | 双击会在“终端”里打开；先执行 `xattr -dr com.apple.quarantine` 清除整个目录的下载隔离标记 |
| Linux | `start.sh` | 无 |

每个压缩包只放本平台的那一个启动文件，用户不会点错。

### 4.4 模型：直接放进压缩包

| 文件 | 大小 | 用途 | 档位 |
| --- | --- | --- | --- |
| `u2net.onnx` | 168 MB | 抠图 | 全部 |
| `embedding-fp32.onnx` | 90 MB | 文本向量（搜索、推荐召回） | 完整 |
| `embedding-int8.onnx` | 23 MB | 文本向量 | 均衡、精简 |
| `embedding-vocab.txt` | 0.1 MB | 词表 | 全部 |
| `image-model-int8.onnx` | 83 MB | 图文模型·图像塔（相似衣物、重复提醒、超级搜索） | 完整、均衡 |
| `image-text-model-int8.onnx` | 98 MB | 图文模型·文本塔（文字找图） | 完整、均衡 |
| `image-text-vocab.txt`、`image-model-manifest.json` | — | 词表、导出记录 | — |

合计约 463 MB。不带 fp32 的图文模型（两个合计约 720 MB），默认配置本来就用 int8。另生成 `models/SHA256SUMS`，
并把每个文件的大小与 SHA-256 写进 `app/build-info.json`，供环境检查核对。

首次启动再下载的方案违反“服务不得自动下载模型”的约定，评委网络也不可控，不采用。

### 4.5 压缩格式

| 平台 | 格式 | 原因 |
| --- | --- | --- |
| Linux | `.tar.gz` | 保留可执行权限，系统自带工具即可解压 |
| macOS | `.zip`（`ditto -c -k --sequesterRsrc --keepParent` 生成） | 访达双击即可解压，ditto 保留可执行权限与扩展属性 |
| Windows | `.zip`（7-Zip 生成） | 资源管理器原生支持 |

模型本身几乎不可压缩，各格式最终体积相差不大。

### 4.6 进程模型：后台服务 + 可随时退出的控制台

两种做法：启动器作为前台“监督进程”一直开着（关窗口即停止），或者服务作为后台进程运行、启动器只是控制台。
采用后者：用户可以关掉菜单窗口而服务继续运行（菜单 0），需要时再打开菜单停止（菜单 2 或 q）。
代价是要可靠地记录与识别进程（6.5），并且要有一个不依赖父子关系的停止方式（4.7）。

### 4.7 停止机制：停止文件

| 方案 | 问题 |
| --- | --- |
| 发信号 SIGTERM | Windows 没有信号；对后台 java.exe 只能 `taskkill /F` 强杀，H2 可能丢失最近约 1 秒的写入 |
| Spring Boot Actuator 的 shutdown 端点 | 要新增依赖，并暴露一个需要额外鉴权与安全配置的 HTTP 入口 |
| 自己写 HTTP 停止接口 | 同样新增网络攻击面，要改 Spring Security 配置 |
| JMX（SpringApplicationAdminMXBean） | 启动器要实现 JMX 客户端，过重 |
| **停止文件** | **采用**。启动器写 `data/run/shutdown`，服务端每秒检查一次，发现后调用 `SpringApplication.exit` 有序退出。没有网络入口，三个系统行为一致 |

停止分三级：停止文件（最多等 40 秒）→ SIGTERM（仅类 Unix，15 秒）→ 强制结束（SIGKILL 或 `taskkill /T /F`）。
`stop --json` 报告实际用了哪一级，CI 要求必须是第一级 `graceful`。

## 5. 包结构

```
yuda-portable-<版本>-<平台>/
  start.bat | start.command | start.sh   本平台的启动文件
  README.txt                             给使用者的说明
  app/
    server.jar                           服务端，含构建好的前端；只含本平台的 OpenCV 与 ONNX Runtime 本地库
    agent/                               Agent：dist、node_modules（生产依赖）、package.json
    launcher/yuda.mjs                    启动器
    build-info.json                      版本、提交、平台、构建时间、Java 与 Node 版本、模型清单（大小、SHA-256、用途）
  runtime/
    java/                                jlink 裁剪的 Temurin 21
    node/                                Node 24（Windows 为 node.exe，其余为 bin/node）
  models/                                第 4.4 节的模型与 SHA256SUMS
  LICENSES/                              第三方许可说明、Node 许可、Java NOTICE
```

运行后才出现的目录：

| 目录 | 内容 | 备份 |
| --- | --- | --- |
| `config/closet.env` | 配置与密钥（权限 0600） | 备份时一并复制 |
| `data/` | H2 数据库、衣物图片、Spring Session；`data/run/` 为运行状态（PID、停止文件），停止时清理 | 是（不含 `data/run`） |
| `logs/` | `server.log`、`agent.log`，超过 10 MB 轮转为 `.1` | 否 |
| `backups/` | 菜单 12 生成的备份 | — |
| `runtime-cache/` | JavaCPP 解压的本地库（`-Dorg.bytedeco.javacpp.cachedir`）、Java 临时目录（`-Djava.io.tmpdir`，ONNX Runtime 在此解压） | 否，可随时删除 |

默认情况下 JavaCPP 会解压到 `~/.javacpp`、ONNX Runtime 会解压到系统临时目录；改到包内后，删除整个文件夹就不会在系统里留下文件。

实测各部分大小（MB）：

| 平台 | app | runtime/java | runtime/node | models | 解压后合计 | 压缩包 |
| --- | --- | --- | --- | --- | --- | --- |
| linux-x64 | 171 | 65 | 121 | 463 | 820 | 565 |
| linux-arm64 | 160 | 65 | 117 | 463 | 805 | 553 |
| macos-arm64 | 160 | 58 | 116 | 463 | 797 | 551 |
| macos-x64 | 168 | 59 | 118 | 463 | 809 | 561 |
| windows-x64 | 199 | 53 | 89 | 463 | 805 | 577 |

## 6. 启动器设计

### 6.1 菜单与命令

无参数运行进入菜单，顶部显示版本、平台、运行状态、访问地址；管理员尚未修改初始密码时多一行账号与初始密码。

```
鱼搭 · 便携版 1.0.0  windows-x64
状态：● 运行中  http://127.0.0.1:8080
初始账号：admin / Xk7mP2qR9vNcT4hW（尚未修改，首次登录后需修改）
──────────────────────────────────────────────
 1. 启动              2. 停止              3. 重新启动
 4. 打开浏览器        5. 运行状态          6. 查看日志
 7. 环境检查          8. 模型压力评估      9. 实时资源监控
10. 设置             11. 重置管理员密码   12. 备份数据
 0. 退出（服务保持后台运行）               q. 停止服务并退出
```

| 命令 | 作用 |
| --- | --- |
| `start [--no-browser]` | 启动（已在运行时只报告地址） |
| `stop` / `restart` | 停止 / 重启 |
| `status` | 进程、端口、内存、CPU、地址、初始密码 |
| `doctor [--verify]` | 环境检查；`--verify` 校验模型 SHA-256 |
| `stress` | 模型压力评估 |
| `monitor [秒]` | 实时资源监控 |
| `logs [server\|agent] [行数]` | 查看日志 |
| `open` | 打开浏览器 |
| `config [get KEY \| set KEY VALUE]` | 读写配置 |
| `reset-password [账号]` | 重置密码 |
| `backup` | 备份数据 |

通用参数：`--json` 输出机器可读结果（CI 依赖它），`--yes` 跳过确认，`--no-browser`。失败时退出码为 1。

菜单的输入自己排队读取：管道输入时（CI 测试菜单）所有行可能在第一次提问前就已到达，直接用 `readline.question`
会丢行；输入结束时把正在等的提问当作“退出”处理。

### 6.2 配置文件

`config/closet.env`，每行 `KEY=VALUE`，`#` 开头为注释，Windows 上按 CRLF 写回。首次需要时（启动、设置、`config set`）
由模板生成：

| 键 | 默认值 | 说明 |
| --- | --- | --- |
| `PORT` / `CLOSET_AGENT_PORT` | 8080 / 8091 | 网页端口 / Agent 内部端口 |
| `YUDA_ACCESS` | `local` | `local` 监听 127.0.0.1；`lan` 监听 0.0.0.0 |
| `YUDA_PROFILE` | `auto` | 模型档位（6.8） |
| `YUDA_OPEN_BROWSER` | `true` | 启动后打开浏览器 |
| `YUDA_JAVA_OPTS` | 空 | 额外 JVM 参数 |
| `CLOSET_BOOTSTRAP_USERNAME` / `PASSWORD` | `admin` / 16 位随机 | 首次启动创建的管理员 |
| `CLOSET_AGENT_SECRET` | 64 位十六进制随机 | 服务端与 Agent 的互信密钥 |
| `CLOSET_YUMG_BASE_URL` / `API_KEY` / `PROTOCOL` / `DEFAULT_MODEL` | 空 | AI 服务，可选 |

`YUDA_*` 只给启动器用；其余键原样作为环境变量交给服务端，所以容器版支持的任何 `CLOSET_*` 都可以写在这里。
优先级：档位推导的默认值 < 配置文件 < 启动器强制项（`PORT`、Agent 地址与回调地址，必须与实际端口一致）。

### 6.3 启动流程

1. 生成或读取配置；若两个服务都在运行，只报告地址与初始密码；若只剩一个，先停止再启动。
2. 检查 Java、jar、Agent 文件是否齐全（缺失时提示“压缩包可能没有完整解压”）。
3. 检查网页端口与 Agent 端口是否空闲（局域网模式按 0.0.0.0 检查），被占用时提示去设置里换端口。
4. 选定档位，创建 `data`、`data/run`、`runtime-cache`，清除残留的停止文件。
5. 以后台进程启动 Agent（只监听 127.0.0.1），日志写 `logs/agent.log`，记录 PID，最多等 30 秒健康检查。
6. 以后台进程启动服务端：

   ```
   java -Xmx<档位> -XX:+ExitOnOutOfMemoryError -Djava.awt.headless=true
        -Dfile.encoding=UTF-8 -Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8
        -Djava.io.tmpdir=runtime-cache/tmp -Dorg.bytedeco.javacpp.cachedir=runtime-cache/javacpp
        -jar app/server.jar --closet.portable.shutdown-file=data/run/shutdown --closet.inference-threads=<N>
   ```

   `stdout.encoding` 必须显式设为 UTF-8：输出重定向到文件时，中文 Windows 默认会按 GBK 写日志。
7. 每 0.5 秒查一次 `/api/health`，最多 300 秒，终端里显示转圈与已等待秒数；进程提前退出就立即判定失败。
8. 任何一步失败：停止已启动的部分，打印对应日志最后 25 行（`--json` 时附 60 行）。
9. 成功：打印耗时与地址（局域网模式另列本机各个局域网地址），提示初始密码（6.6），按配置打开浏览器。

后台进程用 `detached` 启动并 `unref`，Windows 上加 `windowsHide`，菜单退出后服务继续运行。

### 6.4 停止流程

见 4.7。服务端退出后结束 Agent（Agent 无状态，直接 SIGTERM 或 taskkill），删除 `state.json` 与停止文件。

服务端在 `ApplicationReadyEvent` 时会删除残留的停止文件，避免上次遗留的请求把这次启动停掉；因此在服务端就绪之前请求停止，
会在 40 秒后转为下一级。

### 6.5 进程识别

`data/run/state.json` 记录两个 PID、端口、启动时间、档位，以及 `adminReady`、`initialPassword` 两个标志。
PID 可能在重启电脑后被别的程序复用，所以“存活”之外还要核对是不是我们的进程：

| 平台 | 核对方式 |
| --- | --- |
| Linux | 读 `/proc/<pid>/cmdline`，参数里要有本包的 `server.jar` 或 Agent 的 `server.js` 绝对路径 |
| macOS | `ps -ww -p <pid> -o command=`，同上 |
| Windows | `tasklist` 的进程名含 `java` / `node` |

最初的实现按 `ps -o comm=` 的进程名判断，在 Linux 上失败：Node 24 会把主线程命名为 `MainThread`，而 Linux 的 comm 就是主线程名。
CI 抓到后改为核对命令行，同时也比只看进程名更能防止 PID 复用误判。

### 6.6 初始密码提示

需求：管理员没改初始密码之前，启动成功、`status`、菜单顶部都显示账号与初始密码；改过之后不再显示。

启动器无法直接读数据库（服务运行时 H2 文件被锁），所以用接口判断：

1. 取 CSRF 令牌，用配置里的初始密码登录。
2. 返回 200 且 `mustChangePassword=true`：仍是初始密码，显示；随即调用 `/api/auth/logout` 释放会话。
   每个账号最多 5 个会话，超出会挤掉最旧的，不退出就可能把用户自己浏览器里的登录挤掉。
3. 返回 401：密码已改过，写下 `data/.initial-password-changed` 标记，此后不再试登录。
4. 其他情况（超时等）：无法判断，不显示。

坑：服务端的健康检查在 Tomcat 启动后就会通过，而管理员由启动后才执行的 `ApplicationRunner` 创建。首次启动时立刻试登录会得到
401，被误判成“已改密码”，以后再也不提示。所以启动时先等日志里出现本次启动的 `Bootstrap administrator is ready`
（最多 20 秒，`adminReady`），再判断；并且只有 `adminReady` 时才会写“已修改”标记。

菜单每次刷新时，只有上次判断仍是初始密码才会再试，已改过的账号不会因为刷新菜单而被反复登录。

通过启动器重置密码后，新密码写回 `CLOSET_BOOTSTRAP_PASSWORD` 并删除标记，于是重置后的密码在修改前同样每次提示。
`CLOSET_BOOTSTRAP_*` 只在账号不存在时用于创建，改写它没有其他影响。

最初的实现只在“这次启动才新建配置文件”时提示一次：用户若先进设置改端口，配置文件那时就已生成，之后就再也看不到初始密码。
现在的实现覆盖了这种情况，CI 冒烟测试正是先 `config set` 再启动来验证的。

### 6.8 模型压力评估与档位

估算规则与服务端加载图文模型前的检查一致：每个 ONNX 会话常驻内存约为“文件大小 × 1.5”。

| 项目 | 估算 | 常驻 / 按需 |
| --- | --- | --- |
| 服务端 Java | min(堆上限, 900 MB) + 220 MB 非堆 | 常驻 |
| Agent | 110 MB | 常驻 |
| 抠图 U²-Net | 168 × 1.5 ≈ 252 MB | 录入时加载，闲置卸载 |
| 文本向量 | fp32 约 136 MB / int8 约 34 MB | 常驻 |
| 图文模型图像塔、文本塔 | 约 125 MB、147 MB | 使用时加载，闲置卸载 |

“闲置”为常驻部分之和，“峰值”为全部同时加载。以峰值占总内存的比例评级：

| 评级 | 条件 | 建议 |
| --- | --- | --- |
| 轻松 | < 25% | 可放心使用全部本地模型 |
| 适中 | < 45% | 同时批量录入与图片搜索时内存会明显上升 |
| 吃紧 | < 70% | 建议均衡或精简档 |
| 不足 | ≥ 70%，或峰值超过可用内存 512 MB 以上且占比 > 50% | 建议精简档；服务端加载前会检查内存，不够时自动降级 |

CPU：≤ 2 核“偏慢”（抠图单张数秒），≤ 4 核“一般”，其余“充裕”；推理线程数取核数一半，限制在 1–4。

| 档位 | 文本向量 | 图文模型 | 堆上限 | 闲置卸载（抠图 / 图像塔 / 文本塔） | 自动选择 |
| --- | --- | --- | --- | --- | --- |
| full 完整 | fp32 | 开 | 2048 MB | 10m / 10m / 30m | 内存 ≥ 7.5 GB |
| balanced 均衡 | int8 | 开 | 1280 MB | 5m / 5m / 10m | 3.5–7.5 GB |
| lite 精简 | int8 | 关 | 768 MB | 2m / 1m / 1m | < 3.5 GB |

档位通过环境变量落到服务端已有的配置项上（`CLOSET_EMBEDDING_MODEL_PATH`、`CLOSET_IMAGE_MODEL_PATH`、
`CLOSET_*_IDLE_UNLOAD` 等），不需要改服务端代码。精简档把图文模型路径指向一个不存在的文件，服务端按“未安装”处理：
相似衣物改用颜色与轮廓，文字找图关闭，界面有提示。ONNX 推理占用的是 Java 堆外内存，所以 `-Xmx` 不限制模型，只限制业务对象。

实时监控（monitor）每 2 秒采样一次：

| 平台 | 方式 |
| --- | --- |
| Linux、macOS | `ps -o pid=,rss=,%cpu= -p <两个 PID>` |
| Windows | PowerShell `Get-Process`（工作集与累计 CPU 秒数） |

另显示系统可用内存与 1 分钟负载（Windows 没有负载）。CI 实测：五个平台空载、加载全部模型后服务端约 950–1270 MB。

### 6.9 重置密码与备份

两者都需要服务已停止（H2 文件锁、数据库一致性）。服务在运行时，启动器询问后自动停止，完成后自动重启。

- 重置密码复用服务端已有的离线命令 `java -jar server.jar --closet-command=reset-password`，它直接执行 Flyway 迁移
  并更新数据库，不会启动 Web 服务和图像任务。新密码 16 位随机，下次登录必须修改。
- 备份把 `data`（不含 `data/run`）复制到 `backups/data-<时间>`，并附上 `closet.env`。恢复：停止服务，用备份目录替换 `data`，
  把 `closet.env` 放回 `config`，再启动。

### 6.10 访问范围

默认 `local`：服务端只监听 127.0.0.1，系统防火墙不会弹窗，局域网里别人访问不到。改为 `lan` 时监听 0.0.0.0，
启动后列出本机局域网地址；设置菜单里明确提示是 HTTP 明文、同一网络的人都能看到登录页。要求 HTTPS 的功能（便携登录链接）
在局域网地址上不可用，这是服务端已有的安全边界，便携版不放宽。

## 7. 服务端改动

改动刻意保持最小，并且都不影响容器部署。

### 7.1 `com.smartcloset.portable.PortableShutdownWatcher`

- 仅当设置了 `closet.portable.shutdown-file` 时创建（`@ConditionalOnProperty`）；容器部署不设置，类不会加载成 bean。
- `ApplicationReadyEvent` 时先删除残留文件，再用一个守护线程每秒检查一次。
- 发现文件：删除文件，记录 `Portable launcher requested shutdown`，在新的非守护线程里执行
  `System.exit(SpringApplication.exit(context))`。不能在定时器线程里直接退出：`System.exit` 会等待关闭钩子，而关闭过程会等这个定时器。
- 两个构造器：带 `@Autowired` 的给 Spring（取配置与应用上下文），包内可见的给单元测试（注入假的退出动作）。
  第一版漏了 `@Autowired`，Spring 找不到可用构造器，五个平台全部启动失败，第一轮 CI 就暴露了。
- 单元测试 `PortableShutdownWatcherTest`：没有文件时不退出；文件出现后恰好退出一次并删除文件。

### 7.2 `pom.xml` 的 `onnxruntime.version`

ONNX Runtime 从 1.24 起不再发布 macOS x64（Intel）本地库：1.30.0 的 jar 里只有 linux-x64、linux-aarch64、osx-aarch64、win-x64。
在 Intel Mac runner 上冒烟测试时，U²-Net 抠图报 `UnsatisfiedLinkError: no onnxruntime`。逐个检查 Maven Central 上的版本后，
1.23.2 是最后一个带 osx-x64 的版本。版本号改为属性，默认仍是 1.30.0（容器与其他平台不变），只有 macos-x64 包用
`-Donnxruntime.version=1.23.2` 构建。该平台的 U²-Net 抠图与向量模型加载都在 Intel Mac runner 上实测通过。

## 8. 构建流水线（`.github/workflows/portable.yml`）

```
prepare ─┬─ frontend（私有前端仓库：npm test + build:server）──────┐
         ├─ agent（npm test + build，裁剪为生产依赖并打成 tgz）──┤
         ├─ models（下载 / 导出，存入跨系统缓存）─────────────────┼─ package × 5（构建 → 组装 → 压缩 → 解压冒烟测试）─┐
         └─ server-tests（mvn verify，手动运行时可关）─────────────────────────────────────────────────────────┴─ release
```

### 8.1 作业

| 作业 | 内容 |
| --- | --- |
| prepare | 计算版本号（标签 `v1.2.0` → `1.2.0`，否则 `0.0.0-dev.<短提交>`）；按输入筛选平台生成矩阵；计算模型缓存键 |
| frontend | 用只读 deploy key 检出私有前端仓库；`npm ci && npm test && npm run build:server`，通过 `CLOSET_SERVER_DIR` 发布到本仓库的 `static` 与 `person-stickers`；上传为产物 |
| agent | `npm ci && npm test && npm run build`；在新目录 `npm ci --omit=dev --ignore-scripts` 只装生产依赖；打成 tgz 上传，避免产物上传几千个小文件 |
| models | 见 8.2 |
| server-tests | `mvn -B verify`，与 `container.yml` 相同 |
| package | 每个平台一个，见 8.3 |
| release | 标签 `v*`，或手动运行勾选“发布”时执行：下载全部压缩包，生成 `SHA256SUMS.txt`，上传到该标签的 Release；手动发布到预发布版本 `portable-latest`，每次删除重建，只保留最新一份。要求所有 package 成功、服务端测试没有失败 |

### 8.2 模型缓存

- 缓存键 `portable-models-v1-<下载与导出脚本的哈希>`，脚本不变就不重新准备。先用 `lookup-only` 检查，命中时整个作业几秒结束。
- 未命中：运行 `scripts/download-model.sh` 与 `scripts/download-embedding-model.sh`（固定地址与 SHA-256 校验）；
  图文模型先尝试恢复 `deploy.yml` 的导出缓存（同一个键 `image-model-<哈希>`），没有才用 uv 导出（约 6 分钟）。
- 只把要打包的文件收集到 `.portable-models` 存成缓存，开启 `enableCrossOsArchive`：缓存在 Linux 上生成，Windows 也要能恢复。
- 用缓存而不是产物在作业间传递 460 MB 模型：缓存不计入 Actions 存储配额，且五个平台作业共用一份。

### 8.3 平台矩阵与组装

| 平台 | runner | JavaCPP 分类器 | 额外参数 | 压缩 |
| --- | --- | --- | --- | --- |
| linux-x64 | `ubuntu-24.04` | linux-x86_64 | — | tar.gz |
| linux-arm64 | `ubuntu-24.04-arm` | linux-arm64 | — | tar.gz |
| macos-arm64 | `macos-15` | macosx-arm64 | — | zip |
| macos-x64 | `macos-15-intel` | macosx-x86_64 | `-Donnxruntime.version=1.23.2` | zip |
| windows-x64 | `windows-2022` | windows-x86_64 | — | zip |

Windows ARM 暂不提供：JavaCPP 没有 windows-arm64 的 OpenCV 本地库。

每个 package 作业：

1. 安装 Temurin 21 JDK（用于 Maven 与 jlink）和 Node 24（随包携带的就是这份）。
2. 下载前端产物到 `src/main/resources`，下载 Agent 产物，恢复模型缓存（缺失即失败）。
3. `mvn -DskipTests -Dnative.platform=<分类器> package`，构建前确认 `static/index.html` 存在。
4. `node portable/ci/assemble.mjs` 组装：
   - 复制本平台启动文件（加可执行权限）、README、许可说明；
   - 用 `portable/ci/SlimJar.java` 处理服务端 jar：ONNX Runtime 的 jar 里带着所有平台的本地库，还有约 75 MB 的 macOS 调试符号（.dSYM），
     只保留本平台的库。嵌套 jar 必须保持 STORED（Spring Boot 加载器的要求），所以重新计算 CRC 与大小后原样存储。
     每个平台省 41–61 MB；
   - 复制 Agent、启动器、本平台 Node 及其许可；
   - jlink 生成 Java 运行时；macOS 上若签名校验不通过，对每个 Mach-O 文件做 ad-hoc 签名（Apple Silicon 拒绝运行无签名代码）；
     随后实际运行一次 `java -version`；
   - 复制模型并计算 SHA-256，写 `SHA256SUMS` 与 `build-info.json`，打印各部分大小。
5. 压缩，并删除组装目录。
6. 新建目录**重新解压压缩包**，用包内 Node 运行冒烟测试（第 9 节）。测的是用户真正下载到的东西，包括压缩格式是否保留了可执行权限。
7. 写作业摘要（压缩包大小、冒烟测试输出）；失败时上传 `logs/` 与 `config/`（保留 7 天）；成功时上传压缩包（保留 5 天，不再压缩）。

### 8.4 触发与权限

- 自动：修改 `portable/**`、本工作流或 `com.smartcloset.portable` 时，任意分支推送都会运行；推送 `v*` 标签总会运行并发布。
- 手动：Actions → Portable package → Run workflow，可选平台（逗号分隔或 all）、前端分支、是否跑服务端测试、是否发布到 `portable-latest`。
- 同一分支新的推送会取消正在运行的旧运行（`concurrency`）。
- 权限默认 `contents: read`，只有 release 作业有 `contents: write`。
- secret `FRONTEND_DEPLOY_KEY`：前端仓库的**只读** deploy key（2026-10-18 配置）。轮换：在前端仓库 Settings → Deploy keys
  新建只读 key，更新本仓库 secret，删除旧 key。

### 8.4.1 CircleCI 版本（2026-10-22）

GitHub Actions 私有仓库额度用完后，同样的流水线搬到 CircleCI（`.circleci/config.yml`），GitHub 工作流原样保留：

- 任务一一对应：`portable-frontend`、`portable-agent`、`portable-models`、`portable-<平台>` × 5、`portable-release`，
  服务端测试复用日常检查的 `java` 任务；产物经 workspace 传递，模型用 CircleCI 缓存（键与部署任务的图文模型缓存相同）。
- 平台：Linux x64 / ARM 用 `ubuntu-2404` machine，Windows 用 `windows-server-2022-gui`（bash），macOS 用 `m4pro.medium`。
  CircleCI 没有 Intel Mac：`macos-x64` 在 Apple Silicon 上装 x64 的 Node 与 Temurin JDK，经 Rosetta 构建、jlink 与冒烟测试。
- 工具链由 `portable/ci/circleci-tools.sh <平台>` 下载（Node 24 最新版、Temurin 21、Maven 3.9.9），写入
  `~/portable-tools/env.sh` 供后续步骤 source。
- 触发：`v*` 标签随 `release` 工作流运行并发布到该标签；手动 Trigger Pipeline 加参数 `portable=true`，可选
  `portable_platforms`（未选中的平台第一步即停止）、`frontend_ref`、`portable_release`。CircleCI 没有按路径触发，
  改便携相关文件后需手动运行。
- 发布用 `GITHUB_RELEASE_TOKEN`，未设时用 `GHCR_TOKEN`（classic PAT 需含 `repo`）。
- 两边都响应 `v*` 标签，同一时间只启用一边的 tag 发布。

### 8.5 费用

仓库是私有的：macOS runner 按 10 倍、Windows 按 2 倍计费分钟。一轮完整运行约：五个 package 作业各 2–6 分钟，服务端测试约

## 9. 测试设计

### 9.1 冒烟测试（`portable/ci/smoke.mjs`）

在每个平台上，对重新解压出来的包按真实用户的方式操作：命令行调用启动器（`--json` 读结果），并用管道驱动交互菜单。
网页与 Agent 使用 18080、18091 端口，同时验证改端口的配置路径；档位强制设为 `full`，保证全部模型都会加载。

| 步骤 | 验证内容 |
| --- | --- |
| 配置 | `config set` 修改端口与档位（也让配置文件在首次启动前就生成，覆盖 6.6 的情况） |
| 环境检查 | `doctor --verify` 没有失败项（含全部模型的 SHA-256）；`stress` 给出档位与评级 |
| 启动 | `start` 成功并返回耗时；结果里带初始账号与密码 |
| 服务 | 服务端与 Agent 健康；首页（浏览器请求头）与前端路由 `/wardrobe` 返回同一份 index.html；首页引用的 JS 资源可下载；`status` 认出两个进程 |
| 初始密码 | `status` 与菜单顶部显示初始密码 |
| 账号 | 初始管理员登录得到“需要改密码”，修改成功；随后 `status` 不再显示密码，启动器写下“已修改”标记 |
| 本地模型 | GrabCut 抠图（OpenCV 本地库）；U²-Net 抠图（ONNX Runtime 本地库）；60 秒内日志出现“本地向量模型已加载”；`monitor` 采到服务端内存 |
| 菜单 | 管道输入 5（状态）、8（模型压力）、0（退出）：输出含“运行中”与“内存压力”，不再含已修改的密码；退出后服务仍在运行 |
| 重启 | `restart` 成功 |
| 停止 | `stop` 必须是 `graceful`；服务端日志有 `Portable launcher requested shutdown`；端口已释放 |
| 离线操作 | 停止状态下 `reset-password` 与 `backup` 成功，备份含数据库 |
| 再次启动 | 启动结果报告重置后的密码；用它登录得到“需要改密码”；菜单 q 停止服务并退出 |

失败时打印服务端日志最后 80 行并尽量停止服务；工作流同时上传日志目录。

测试用图在脚本里用 zlib 现场生成（96×96 PNG，灰底红色方块），不往仓库里加图片文件。

## 11. 安全与隐私

- **密钥**：`closet.env` 以 0600 权限创建，包含 Agent 密钥、初始密码和可能的 AI 服务密钥；README 与文件头提醒不要外传。
  初始密码以明文保存是有意的取舍：便携版面向单人本机使用，密码首次登录必须修改，修改后这个值不再生效。
- **网络**：默认只监听 127.0.0.1，Agent 永远只监听 127.0.0.1。停止机制是文件，没有新增任何网络入口。
- **初始密码探测**：只在本机回环地址进行，登录后立即退出，确认已修改后永久停止探测（6.6）。
- **局域网模式**：明确提示 HTTP 明文；HTTPS 相关的安全边界由服务端保持不变。
- **CI**：前端仓库只给只读 deploy key；工作流默认只读权限，仅 release 作业可写。
- **管理接口**：保持默认关闭，便携版不打开 `/api/manage/v1`。

## 12. 已知限制与后续

| 限制 | 影响 | 后续 |
| --- | --- | --- |
| 未做代码签名与公证 | macOS 第一次要右键 `start.command` → 打开；Windows 可能出现 SmartScreen“已保护你的电脑” | 申请 Apple Developer ID 做公证；Windows 代码签名证书 |
| runner 上的文件没有下载隔离标记 | 6.7 的隔离检查与 `start.command` 的解除逻辑没有在 CI 中真正触发 | 发布前在真实 Mac 上下载一次压缩包验证 |
| 菜单只在管道输入下测试 | 真实终端里的颜色、转圈、按回车返回、日志跟踪未经 CI 验证 | 发布前人工过一遍 |
| AI 服务未参与测试 | Agent 对话、识别、生图需要密钥 | 可用测试密钥加一个可选冒烟步骤 |
| 图文模型只做了文件校验 | 没有在冒烟测试里实际跑相似衣物、文字找图 | 冒烟测试增加录入衣物并触发图像向量 |
| Release 发布步骤还没跑过 | 推送标签或勾选发布时首次执行 | 第一次发布时检查 Release 附件 |
| 无 Windows ARM | 需要 OpenCV windows-arm64 本地库 | 等 JavaCPP 支持 |
| macOS Intel 使用较旧的 ONNX Runtime 1.23.2 | 与其他平台推理结果可能有极小差异 | Intel Mac 淘汰后去掉该平台 |
| 不支持原地升级 | 升级要把 `data` 和 `config` 拷到新版本目录 | 启动器增加“从旧版本导入数据” |
