# 衣物图片加载优化设计

## 问题

衣柜列表、推荐、搭配素材栏直接加载处理后的原图：抠图贴纸是带透明通道的 PNG，常见 1–3 MB、1000–2000 像素，而卡片实际只有 100–300 像素宽。图片缓存只有 1 小时，过期后整张重新下载；`/assets` 下带哈希的脚本样式也没有长缓存，JS/CSS/JSON 也没有压缩。

## 方案

### 缩略图与原图分离（`?w=`）

- 共享图片接口支持可选参数 `w`：`/api/workflows/{id}/files/{name}`、`/api/batches/{id}/files/{name}`、`/api/segmentations/{id}/files/{name}`、`/api/segmentations/{id}/sticker/image`。不带 `w` 时行为不变。
- 宽度向上取整到 160 / 320 / 480 / 720 / 960 之一，只缩小不放大；读入时先按 2 倍目标宽度降采样，再用 OpenCV `INTER_AREA` 缩放，保留 EXIF 方向与透明通道。
- 格式按 `Accept` 协商：浏览器接受 `image/webp` 时输出 WebP（质量 82，带透明）；否则透明 PNG 仍为 PNG，JPEG 为渐进式 JPEG。响应带 `Vary: Accept`。
- 实现 `com.smartcloset.storage.ImageVariants`：副本只是本机缓存（`{storage-dir}/cache/image-variants/`），无论原图在本地还是存储桶；文件名由原图 key 与版本（本地为大小+修改时间，存储桶为上传时记录的 sha256）求哈希，原图被重写就生成新副本。目录可随时删除，不参与存储迁移。编码并发限制为 CPU 核数的一半。
- 原图无法解码时退回原图，不让卡片失败。个人照片、基准人物、试穿结果仍走 `personal`（no-store），不提供副本。

实测：1024 px、2.1 MB 的 PNG 结果图，480 宽 WebP 约 18 KB，960 宽约 62 KB；首次生成约 200–250 ms，之后直接读缓存。

### 浏览器缓存

- 本地原图与副本：`Cache-Control: private, max-age=86400` + `ETag`；过期后浏览器带 `If-None-Match` 重新验证，未变化返回 304，不再重传图片。
- 存储桶直链跳转保持原规则（不超过链接有效期）。
- `/assets/**`（文件名带内容哈希）：`public, max-age=31536000, immutable`；`index.html` 等无哈希文件保持默认重新验证，发版即时生效。
- 未开启 Tomcat 自带压缩：它会把 Spring 写的 `Vary: Origin` 覆盖成 `Vary: accept-encoding`，跨域缓存会出错（ClosetCorsApiTest 守护）。JS/CSS/JSON 压缩交给前置代理（cloudflared / nginx）。

### 前端

- `src/domain/image-variants.ts`：`variantPath` / `variantSrcset`，只给上述可缩放接口加 `w`，blob:、data:、私有照片原样返回；`services/urls.ts` 导出 `thumbUrl`、`thumbSrcset`。
- 衣柜卡片（`GarmentArt`）使用 `srcset` 320/480/720 与按栅格列数写的 `sizes`，浏览器按卡片宽度与屏幕密度挑选；仍为 `loading="lazy"`、`decoding="async"`。
- 小缩略图（推荐、相似衣物、整理建议、搭配图层与素材栏、任务列表、批量结果、展示图候选）用 320 或 160 副本并懒加载。
- 衣物详情页的预览用 960 副本；“查看原始大图”链接、穿搭画板（需要原始像素与导出质量）继续使用原图。

### 预生成缩略图

`GarmentThumbnailWarmer` 在后台低优先级线程上，每 15 秒（启动后先等 30 秒）查一次 `garment.updated_at_ms` 比上次更新的衣物，为展示图预生成衣柜卡片用的 320/480/720 WebP 副本。所有改展示图的路径（处理完成、快速入柜、选择展示图、确认入柜）都会更新 `updated_at_ms`，所以无需在各处埋点；水位从 0 开始，服务启动后的第一轮会把现有衣柜补齐。已有副本只需一次文件检查；无法解码的图片跳过，访问时退回原图。可用 `closet.image-variants.prewarm=false` 关闭，间隔由 `closet.image-variants.prewarm-interval-seconds` 调整。

### 推荐卡片直接带展示图地址

推荐结果中每件单品（`GarmentView`）新增 `displayUrl`，换一件的候选同样带上；每套搭配一次批量查询，只用于展示，不参与召回与打分。前端 `GarmentThumb` 收到 `displayUrl` 时直接显示，不再逐件请求衣物详情；旧后端不返回该字段时仍按原方式获取。发给模型的推荐摘要（`compactOutfit`）只有名称和颜色，不包含图片地址。

助手的两种衣物卡片同样带上地址：`search_wardrobe` 的选择卡（`GARMENT_CHOICE`，每个候选的 `displayUrl`）与 `closet_summary` 的清单卡（`GARMENT_LIST`，每项的 `displayUrl`）。地址只写进卡片 payload：agent-runtime 把 `choiceCard` / `listCard` 推给浏览器后，在交给模型的工具结果里替换成一句说明；模型可见的 `items` 列表不加字段（AgentApiTest 守护）。批量查询收拢到 `GarmentRepository.displayUrls`，带 owner 时只返回该用户的衣物。改动前已保存的卡片没有该字段，前端仍逐件获取。
