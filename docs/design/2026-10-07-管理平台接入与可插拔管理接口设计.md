## 1. 背景与目标

鱼搭目前只有面向终端用户的界面和一个极简的 `/admin/processing` 页面，账号管理只能通过命令行 `ClosetAccountCli` 完成，也没有任何跨用户的统计视图。本次要提供一个完整的后台管理平台，满足两类需求：

1. **业务用户管理**：管理员能查看、创建、启用/禁用业务用户，重置密码，强制下线，管理便携登录链接，调整 AI 额度。
2. **衣柜洞察（方向 B）**：全站汇总的衣柜构成、搭配使用、录入采纳和 AI 用量，并支持按用户下钻查看单人衣柜报告。

为避免从零写后台，复用两个现成项目：

- start 已有 JWT、Refresh Token、数据库 RBAC、审计、限流、IP 防护、运行状态检查、导航菜单下发；
- admin 已有布局、登录、菜单、标签页、权限指令、表格与 ECharts。

### 1.1 核心约束：鱼搭必须可插拔

> 鱼搭离开 start/admin 后，仍能单独运行，并能较顺利地接入其他宿主平台。

由此推出的硬性原则：

| 原则 | 含义 |
|---|---|
| P1 默认关闭 | 管理接口模块默认不加载；关闭时鱼搭行为与现状完全一致 |
| P2 中立契约 | 鱼搭只暴露通用、带版本的 HTTP 接口，不出现 start/admin 的任何概念（信封结构、权限码、审计表、菜单） |
| P3 标准语义 | 错误用 RFC 9457 Problem Details；分页、时间、追踪头使用通用约定 |
| P4 认证可插拔 | 通过 `ManagementAuthenticator` 接口选择认证方式，第一期实现 HMAC 签名 |
| P5 契约优先 | `docs/management-api.yaml`（OpenAPI 3.1）是唯一契约；契约测试保证实现一致 |
| P6 单向依赖 | 核心包不依赖 `management` 包；删除整个包后项目仍可编译运行（ArchUnit 守护） |
| P7 适配在外 | 一切格式转换、权限、审计、降级都在宿主侧（start）完成 |

同样，start 和 admin 侧的鱼搭集成也做成可插拔：开关关闭或删除集成目录后，它们回到原模板状态。

### 1.2 非目标

- 不把 start 改造成统一身份中心，不让鱼搭改用 JWT 登录（终端用户登录、会话、CSRF、便携登录保持现状）。
- 不合并两个后端的代码或数据库；不让 start 直接访问鱼搭的 H2 文件（H2 文件库仅允许单进程打开）。
- 第一期不做用户物理删除、批量操作、管理端修改用户衣物内容。
- 第一期不实现 JWT 认证模式（只预留接口与配置项）。
- 不做 1920 大屏；洞察以后台常规页面呈现。

## 2. 总体架构

```
┌──────────────────────┐   JWT (Bearer)    ┌──────────────────────────────┐  HMAC 签名请求   ┌──────────────────────────────┐
│ springboot-admin     │ ───────────────▶ │ springboot-start              │ ──────────────▶ │ smart-closet-server           │
│ views/integrations/  │ ◀─────────────── │ modules/integrations/closet   │ ◀────────────── │ com.smartcloset.management    │
│   closet/*           │ {data,traceId}   │  · @PreAuthorize closet:*     │ JSON / Problem  │  · ManagementSecurityConfig   │
└──────────────────────┘                  │  · AuditService               │   Details       │  · /api/manage/v1/**          │
                                          │  · RestClient + 降级          │                 │  · 调用核心 service           │
                                          │  · RuntimeComponent 健康检查  │                 └──────────────┬───────────────┘
                                          └──────────────────────────────┘                                │
                                                                                                         ▼
                                                                                              H2：closet_user / garment / outfit ...
```

请求链路（以“禁用用户”为例）：

1. admin 调 `PATCH /api/v1/closet/users/{username}/status`，携带 start 的 Access Token。
2. start 依次经过 Trace ID、IP 规则、接口开关、限流、JWT 认证，`@PreAuthorize("hasAuthority('closet:user:write')")` 校验权限。
3. start 的 `ClosetUserAdministrationService` 用 `ClosetManagementClient` 签名并调用鱼搭 `PATCH /api/manage/v1/users/{username}/status`，透传 `X-Request-Id`（= start traceId）和 `X-Operator`（= start 管理员用户名）。
4. 鱼搭校验签名，调用核心 `ClosetAccountService.setEnabled`，同一事务内吊销便携链接、删除会话；写一条管理操作日志。
5. 鱼搭返回 JSON；start 记审计事件 `CLOSET_USER_DISABLED`，包装 `{data, traceId, timestamp}` 返回 admin。
6. 鱼搭不可达 / 超时 / 5xx 时，start 返回 `503 CLOSET_SERVICE_UNAVAILABLE`，审计记 `FAILURE`。

部署拓扑：三个进程。鱼搭监听 `127.0.0.1` 或仅内部网络；start 对外；admin 静态资源由 nginx 或 start 托管。

### 3.2 配置

```yaml
closet:
  management:
    enabled: ${CLOSET_MANAGEMENT_ENABLED:false}
    auth:
      mode: hmac                       # 第一期仅 hmac；jwt 预留
      clock-skew: 300s                 # 时间戳允许偏差
      nonce-ttl: 600s                  # nonce 记忆时长，需 ≥ 2×clock-skew
      keys:                            # 支持多把密钥轮换
        - id: ${CLOSET_MANAGEMENT_KEY_ID:primary}
          secret: ${CLOSET_MANAGEMENT_SECRET:}
    max-body-bytes: 65536
    insights-cache-ttl: 60s
```

启动校验（`ManagementProperties` 构造器内）：

- `enabled=true` 时至少一把密钥，`secret` 按 UTF-8 原文字节参与 HMAC，长度不少于 32 字节（推荐 `openssl rand -base64 48` 生成后原样使用），否则启动失败并给出中文提示；
- `mode` 只能是 `hmac`（`jwt` 给出“尚未实现”的明确错误）；
- `nonce-ttl ≥ 2 × clock-skew`。

`ClosetEnvironmentPostProcessor` 现有的环境变量映射表追加 `CLOSET_MANAGEMENT_ENABLED`、`CLOSET_MANAGEMENT_KEY_ID`、`CLOSET_MANAGEMENT_SECRET`；同步 `.env.example`、`compose.yaml`、`docs/INDEPENDENT_DEPLOYMENT.md`。

### 3.3 安全链

`ManagementSecurityConfiguration` 只在开关打开时注册一条独立的 `SecurityFilterChain`：

```java
@Bean @Order(1)
SecurityFilterChain managementSecurity(HttpSecurity http, ManagementAuthenticationFilter filter, ...) {
    http.securityMatcher("/api/manage/**")
        .csrf(c -> c.disable())                       // 无 Cookie、无浏览器调用
        .cors(c -> c.disable())                       // 不允许浏览器跨域直调
        .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
        .requestCache(c -> c.disable())
        .securityContext(c -> c.requireExplicitSave(true))
        .addFilterBefore(filter, AnonymousAuthenticationFilter.class)
        .authorizeHttpRequests(a -> a.anyRequest().hasAuthority("MANAGEMENT"))
        .exceptionHandling(...写 Problem Details...);
    return http.build();
}
```

- 现有 `closetSecurity` 链不改；未开启时 `/api/manage/**` 落入主链：匿名请求 401，已登录请求 404（无 handler）。
- `ManagementAuthenticationFilter` 先用 `ContentCachingRequestWrapper` 的替代实现（自定义一次性读取并缓存，超过 `max-body-bytes` 直接 413）读取 body，再交给 `ManagementAuthenticator`。
- 鉴权成功后 `SecurityContext` 放入 `ManagementPrincipal`，权限 `MANAGEMENT`。管理接口内部 **不调用** `ClosetIdentity.username()`，避免把管理调用误当成某个业务用户。

### 3.4 HMAC 签名协议

请求头：

| 头 | 必填 | 说明 |
|---|---|---|
| `X-Closet-Key-Id` | 是 | 密钥 ID |
| `X-Closet-Timestamp` | 是 | Unix 毫秒 |
| `X-Closet-Nonce` | 是 | 16–64 位 `[A-Za-z0-9_-]` |
| `X-Closet-Signature` | 是 | `base64url(HMAC-SHA256(secret, canonical))`，无填充 |
| `X-Operator` | 否 | 宿主侧操作人标识，≤128 字符、单行；参与签名 |
| `X-Request-Id` | 否 | 追踪 ID，≤128 字符、`[A-Za-z0-9._:-]`；不合法时鱼搭生成新 ID；参与签名 |

规范串（各行以 `\n` 连接，末尾无换行）：

```
CLOSET-HMAC-SHA256
{HTTP 方法大写}
{原始路径，不含 query，不解码}
{规范化 query：按参数名、再按值字典序排序，RFC 3986 编码，name=value 用 & 连接；无则空串}
{timestamp}
{nonce}
{X-Operator，缺省为空串}
{X-Request-Id，缺省为空串}
{body 的 SHA-256 十六进制小写；空 body 为空串的哈希 e3b0c442…b855}
```

校验顺序与错误：

1. 头缺失或格式错误 → 401 `MANAGEMENT_SIGNATURE_MISSING`
2. 未知 key id → 401 `MANAGEMENT_KEY_UNKNOWN`
3. 时间戳偏差 > `clock-skew` → 401 `MANAGEMENT_TIMESTAMP_SKEWED`
4. 签名不匹配（`MessageDigest.isEqual` 常量时间比较）→ 401 `MANAGEMENT_SIGNATURE_INVALID`
5. nonce 在 `nonce-ttl` 内已出现 → 401 `MANAGEMENT_REPLAYED`（签名通过后才登记 nonce，防止未认证请求污染缓存）

`ReplayGuard`：`ConcurrentHashMap<String key, Long expiresAt>`，上限 100 000 条，满时先清理过期项，仍满则拒绝（503 `MANAGEMENT_BUSY`）。鱼搭是单实例部署，内存去重足够；多实例时需替换为数据库或 Redis 实现，接口已隔离。

仓库提供 `scripts/manage-curl.sh`：读取环境变量中的密钥，为任意请求计算签名后调用 curl，用于验收“脱离 start 也能调用”。

### 3.5 通用约定

- **基础路径**：`/api/manage/v1`
- **内容类型**：请求 `application/json`；成功响应 `application/json`；错误响应 `application/problem+json`
- **时间**：所有时间字段为 Unix 毫秒，字段名以 `AtMs` 结尾（与鱼搭现有约定一致）；日期参数 `from`/`to` 为 `YYYY-MM-DD`，按 `Asia/Shanghai` 解释，`to` 含当天
- **分页**：请求 `page`（从 1 开始，默认 1）、`size`（1–100，默认 20）；响应 `{ "items": [...], "total": 123, "page": 1, "size": 20 }`
- **追踪**：响应总是回写 `X-Request-Id`
- **幂等**：状态类写操作（启用/禁用、角色、额度）天然幂等；创建用户对已存在用户名返回 409

错误体：

```json
{
  "type": "urn:closet:problem:user-not-found",
  "title": "用户不存在",
  "status": 404,
  "detail": "用户 alice 不存在。",
  "code": "USER_NOT_FOUND",
  "requestId": "…",
  "violations": [{ "field": "size", "message": "不能大于 100" }]
}
```

错误码表（管理接口专用，`code` 为稳定契约）：

| HTTP | code | 场景 |
|---|---|---|
| 400 | `VALIDATION_FAILED` | 参数/请求体校验失败，带 `violations` |
| 400 | `MALFORMED_JSON` | JSON 无法解析或含未知字段 |
| 401 | `MANAGEMENT_*` | 见 3.4 |
| 404 | `USER_NOT_FOUND` | 目标用户不存在 |
| 404 | `PORTABLE_LINK_NOT_FOUND` | 便携链接不存在或不属于该用户 |
| 409 | `USER_ALREADY_EXISTS` | 创建重名 |
| 409 | `LAST_ADMIN_PROTECTED` | 禁用或降级最后一个启用的 ADMIN |
| 413 | `PAYLOAD_TOO_LARGE` | 超过 `max-body-bytes` |
| 503 | `MANAGEMENT_BUSY` | nonce 缓存饱和 |
| 500 | `INTERNAL_ERROR` | 未预期异常，`detail` 不泄露堆栈 |

`ManagementProblemHandler` 用 `@RestControllerAdvice(basePackages = "com.smartcloset.management")` 且 `@Order(HIGHEST_PRECEDENCE)`，不影响现有 `ApiExceptionHandler` 的 `{code,message}` 结构。

### 3.6 用户管理接口

#### `GET /users`

查询参数：`q`（用户名包含，忽略大小写）、`status`（`ENABLED`|`DISABLED`）、`role`（`USER`|`ADMIN`）、`sort`（`createdAt`|`username`|`lastActiveAt`，默认 `createdAt`）、`order`（`asc`|`desc`，默认 `desc`）、`page`、`size`。

```json
{
  "items": [{
    "username": "alice",
    "role": "USER",
    "enabled": true,
    "mustChangePassword": false,
    "createdAtMs": 1790000000000,
    "lastActiveAtMs": 1790100000000,
    "activeSessionCount": 2,
    "garmentCount": 48,
    "outfitCount": 6
  }],
  "total": 1, "page": 1, "size": 20
}
```

- `lastActiveAtMs` = 该用户未过期会话 `MAX(LAST_ACCESS_TIME)`，无会话为 `null`。它是近似值：会话过期被清理后会丢失，文档与界面需注明“最近会话活跃”。
- `garmentCount` 只计 `closet_status='ACTIVE'`。
- 实现：一条分页 SQL 取当页用户，再用 `IN (…)` 批量查当页的会话、衣物、穿搭计数，避免 N+1。过滤与排序全部进 SQL（`lastActiveAt` 排序使用左连接子查询）。

#### `GET /users/{username}`

```json
{
  "username": "alice", "role": "USER", "enabled": true, "mustChangePassword": false,
  "createdAtMs": 0, "lastActiveAtMs": 0, "activeSessionCount": 2,
  "garments": { "ACTIVE": 48, "DRAFT": 3, "TRASHED": 1 },
  "outfitCount": 6, "outfitPlanCount": 4, "quickIntakeCount": 30,
  "hasWearerProfile": true,
  "activePortableLinkCount": 0,
  "quota": { "image": { "limit": 20, "used": 3, "overridden": false }, "agent": { "limit": 30, "used": 0, "overridden": false }, "resetAtMs": 0 }
}
```

`garments` 的键为数据库中实际出现的 `closet_status`，不硬编码。

#### `POST /users`

请求：`{ "username": "bob", "role": "USER", "password": null }`

- `password` 为空时生成 20 位随机临时密码（`SecureRandom`，字母数字），只在本次响应中返回一次；
- 新用户 `must_change_password = 1`；
- 响应 201，`Location: /api/manage/v1/users/bob`，体 `{ "username": "bob", "temporaryPassword": "…" | null }`。

#### `PATCH /users/{username}/status`

请求：`{ "enabled": false }`。禁用时：更新标志 → 吊销便携链接 → 删除全部会话（同一事务）。最后一个启用的 ADMIN 不可禁用。响应：`{ "username": "alice", "enabled": false, "revokedSessions": 2 }`。

#### `PATCH /users/{username}/role`

请求：`{ "role": "ADMIN" }`。降级最后一个启用 ADMIN → 409。角色变化后删除该用户会话（权限随会话缓存）。

#### `POST /users/{username}/password-reset`

请求：`{ "password": null }`（为空则生成临时密码）。效果：`must_change_password = 1`、吊销便携链接、删除会话。响应：`{ "username": "alice", "temporaryPassword": "…" | null, "revokedSessions": 1 }`。

#### `GET /users/{username}/sessions` / `DELETE /users/{username}/sessions`

GET 返回未过期会话：`[{ "sessionRef": "SHA-256(PRIMARY_ID) 的前 16 位十六进制", "createdAtMs", "lastAccessAtMs", "expiresAtMs", "portable": false }]`。不暴露 `SESSION_ID`。`portable` 依据会话属性 `portableLoginLinkId` 是否存在。DELETE 删除全部会话，返回 `{ "revokedSessions": n }`。

#### `GET /users/{username}/portable-links` / `DELETE /users/{username}/portable-links/{id}`

复用 `PortableLoginService.Link` 字段：`id, createdAt, expiresAt, sessionExpiresAt, status`，对外改名为 `createdAtMs` 等以保持约定。DELETE 成功 204，不存在 404。

#### `GET /users/{username}/quota` / `PUT /users/{username}/quota`

PUT 请求：`{ "imageDailyLimit": 50, "agentDailyLimit": null }`，`null` 表示恢复默认；范围 0–1000。响应同 GET：`{ "image": {limit, used, overridden}, "agent": {…}, "resetAtMs" }`。

新表（Flyway `V14__management.sql`）：

```sql
CREATE TABLE closet_user_quota (
  owner_username VARCHAR(80) PRIMARY KEY REFERENCES closet_user(username) ON DELETE CASCADE,
  image_daily_limit INTEGER,
  agent_daily_limit INTEGER,
  updated_at_ms BIGINT NOT NULL,
  CHECK (image_daily_limit IS NULL OR image_daily_limit BETWEEN 0 AND 1000),
  CHECK (agent_daily_limit IS NULL OR agent_daily_limit BETWEEN 0 AND 1000)
);
CREATE TABLE management_operation_log (
  id VARCHAR(36) PRIMARY KEY,
  occurred_at_ms BIGINT NOT NULL,
  key_id VARCHAR(64) NOT NULL,
  operator VARCHAR(128),
  request_id VARCHAR(128),
  action VARCHAR(64) NOT NULL,
  target_username VARCHAR(80),
  result VARCHAR(16) NOT NULL,
  detail VARCHAR(1000)
);
CREATE INDEX idx_management_log_time ON management_operation_log(occurred_at_ms);
CREATE INDEX idx_closet_user_created ON closet_user(created_at_ms);
-- SPRING_SESSION(PRINCIPAL_NAME) 已由 V5 的 SPRING_SESSION_IX3 覆盖，无需新增
```

> 迁移始终执行（与开关无关），保证开关切换不需要改库；表很小，对单独运行无影响。`QuotaPolicy` 也读取 `closet_user_quota`，因此该表属于核心而非管理模块，命名上不带 `management`。

管理日志只记录写操作，`detail` 不写密码与临时密码。保留期第一期不清理（量极小），后续可加定时清理。

### 3.7 洞察接口（只读）

所有洞察接口共享参数 `username`（可选，缺省为全站）与 `from`/`to`（缺省为最近 30 天，跨度上限 366 天）。结果按“参数组合”缓存 `insights-cache-ttl`（Caffeine 不引入，使用简单的带时间戳 `ConcurrentHashMap`，上限 500 项）。

数据口径声明（同时写入 OpenAPI 描述和前端说明）：

- 鱼搭**没有穿着记录**。“使用”指衣物出现在已保存搭配（`outfit.scene_json` 中的 `garmentId`）的次数；OOTD 计划另计。
- 衣物分类沿用 `ClosetClassification`（`closet-families-v1`），颜色取 `primaryColor`，季节取 `seasons`，与用户端统计口径一致。
- 采纳率 = 区间内创建的衣物中当前为 `ACTIVE` 的比例；反映“用户逐件采纳”这一产品成功指标，但会受用户后续删除影响，界面需注明。

#### `GET /insights/overview`

```json
{
  "scope": { "username": null, "from": "2026-09-08", "to": "2026-10-07" },
  "users": { "total": 12, "enabled": 11, "activeInRange": 7, "createdInRange": 2 },
  "garments": { "active": 420, "draft": 31, "createdInRange": 88, "adoptedInRange": 70, "adoptionRate": 0.795 },
  "outfits": { "total": 64, "createdInRange": 15 },
  "outfitPlans": { "createdInRange": 9 },
  "quickIntakes": { "createdInRange": 120 },
  "ai": { "imageUnitsInRange": 230, "agentMessagesInRange": 140 },
  "generatedAtMs": 0, "mappingVersion": "closet-families-v1"
}
```

`activeInRange` 依据会话最近访问时间，与列表口径一致；指定 `username` 时 `users` 字段省略。

#### `GET /insights/wardrobe`

衣柜构成（只统计 ACTIVE）：

```json
{
  "scope": { "username": null },
  "totalActive": 420,
  "categories": [{ "key": "TOP", "count": 120 }],
  "colors": [{ "key": "黑色", "count": 80 }],
  "seasons": [{ "key": "春", "count": 200 }],
  "unknownCategoryCount": 12, "unknownSeasonCount": 30,
  "favoriteCount": 40,
  "wearingConfirmedCount": 100,
  "mappingVersion": "closet-families-v1"
}
```

实现复用 `GarmentRepository.projection(owner)`：全站时按用户遍历（每用户一条查询）并合并。颜色返回前 20 项，其余并入 `其他`。规模假设：≤ 200 用户、≤ 2 万件衣物；超出时改为批量投影查询（接口不变）。

#### `GET /insights/usage`

```json
{
  "scope": { "username": "alice" },
  "outfitCount": 6,
  "topUsed": [{ "garmentId": "…", "owner": "alice", "name": "白衬衫", "family": "SHIRT", "outfitCount": 4 }],
  "idle": { "count": 30, "ratio": 0.62, "sample": [{ "garmentId": "…", "owner": "alice", "name": "…", "family": "PANTS", "createdAtMs": 0 }] },
  "byFamily": [{ "key": "TOP", "active": 120, "usedInOutfits": 60 }]
}
```

`topUsed` 前 10，`idle.sample` 前 20（按创建时间升序，越早越“吃灰”）。全站视图下 `owner` 字段用于下钻。不返回图片 URL（图片需要业务用户会话才能访问，管理端第一期不展示衣物图）。

#### `GET /insights/trends`

参数：`metric`（`garments_created`|`garments_adopted`|`outfits_created`|`quick_intakes`|`image_units`|`agent_messages`|`users_created`，可重复传多个）、`granularity`（`day`|`week`，默认 `day`）。

```json
{
  "granularity": "day",
  "buckets": ["2026-10-01", "2026-10-02"],
  "series": [{ "metric": "garments_created", "values": [3, 5] }]
}
```

空桶补 0；周以周一为起点。`image_units` 来自 `ai_daily_quota.used`，`agent_messages` 来自 `agent_daily_quota.used`。

### 4.5 协议转换

- 成功：鱼搭 JSON 原样成为 `data`，由 start 现有 `ApiResponseAdvice` 包装 `{data, traceId, timestamp}`。分页结构转换为 start 的 `PageResponse`：`items → items`、`page(1 起) → page(0 起，start 的 PageResponse 使用 Spring Data 页码)`；start 接收的 `page` 参数同样 0 起，转发时 +1、`total → totalElements`、`totalPages = ceil(total/size)`。
- 失败：`ClosetProblemTranslator` 将 Problem Details 映射为 start `ApiException`：

| 鱼搭 | start |
|---|---|
| 400 `VALIDATION_FAILED`（含 violations） | 400 `VALIDATION_FAILED`（violations 透传） |
| 404 `USER_NOT_FOUND` / `PORTABLE_LINK_NOT_FOUND` | 404 `NOT_FOUND`，message 用鱼搭 `detail` |
| 409 `USER_ALREADY_EXISTS` | 409 `CONFLICT` |
| 409 `LAST_ADMIN_PROTECTED` | 409 `CLOSET_LAST_ADMIN_PROTECTED`（新增错误码） |
| 401 `MANAGEMENT_*` | 502 `CLOSET_INTEGRATION_MISCONFIGURED`（新增；属于服务间配置错误，不能当作管理员未登录） |
| 5xx、连接失败、超时 | 503 `CLOSET_SERVICE_UNAVAILABLE`（新增） |

- 新增 `ApiErrorCode`：`CLOSET_SERVICE_UNAVAILABLE(503)`、`CLOSET_INTEGRATION_MISCONFIGURED(502)`、`CLOSET_LAST_ADMIN_PROTECTED(409)`。
- 请求转发头：`X-Request-Id = 当前 traceId`，`X-Operator = 当前管理员 username`。
- start 侧再做一层入参校验（用户名正则、`size ≤ 100`、额度范围），尽早失败；鱼搭侧校验仍是最终防线。

### 4.6 健康检查

`ClosetRuntimeComponent`：`code=closet-service`，`kind=SERVICE_DEPENDENCY`，`check()` 发起签名的 `GET /api/manage/v1/users?size=1`，2 秒超时；成功返回 `up("鱼搭管理接口可用")`，失败返回 `error(原因摘要)`，不包含密钥。

## 7. 安全考量

- 管理接口只接受签名请求；鱼搭默认监听 `127.0.0.1`，部署时管理接口不应暴露到公网。如必须经过反向代理，代理层对 `/api/manage/**` 做来源 IP 限制。
- 密钥只经环境变量注入，不写入仓库、日志、审计、启动摘要；`.env.example` 给出生成方法（`openssl rand -base64 48`）。
- 临时密码只在一次响应中出现：鱼搭不记录、start 不审计、admin 不缓存（不进 Pinia 持久化、不进路由参数）。
- `X-Operator`、`X-Request-Id` 做长度与字符校验，写日志前去除控制字符，避免日志注入。
- 禁用、重置密码、改角色立即撤销会话；便携登录链接同时吊销。
- 管理接口不返回衣物图片、原图或私密媒体（`private_media`、`person_baseline`）链接；个人体型资料只返回“是否已填写”。
- 鱼搭侧对 `/api/manage/**` 不启用 CORS，浏览器无法直接调用。

## 10. 实现记录（M1–M3，2026-10-07）

与上文设计相比的落地细节：

- **Bean 开关**：管理包内每个 Spring Bean（配置、控制器、服务、异常处理）都标注 `@ConditionalOnManagementEnabled`，而不是只在入口配置上加条件，因为组件扫描会绕过入口配置。`ManagementArchitectureTest` 用 ArchUnit 同时检查“核心不依赖管理包”和“管理包内所有 `@Component` 派生类都带开关注解”。
- **鉴权过滤器不是 Bean**：`ManagementAuthenticationFilter` 在安全链内手工构造，避免 Spring Boot 自动把 Filter Bean 注册为全局 Servlet 过滤器。
- **严格 JSON**：应用级 `ObjectMapper` 忽略未知字段，Jackson 3 下 `@JsonIgnoreProperties(ignoreUnknown = false)` 无法覆盖。管理接口的请求体由 `StrictJsonBodies` 以 `FAIL_ON_UNKNOWN_PROPERTIES`、`FAIL_ON_TRAILING_TOKENS` 读取，再交给 Bean Validation，用户端行为不受影响。
- **签名规范化 query**：先按表单规则解码（`+` 视为空格），再按 RFC 3986 编码；排序键是编码后的参数名，其次编码后的值。跨实现测试向量（见 `HmacCanonicalTest.sharedTestVector`）：密钥 `0123456789abcdef0123456789abcdef`，签名 `QrNFOGRrxbMHYQK3h_5AzEq2QbFkYErcWAuygoZ8r88`。
- **额度**：`QuotaPolicy` 取代了 `QuotaController`、`ProcessingStore`、`PersonalRenders`、`WorkflowRepository` 中的常量 `20` 与 `AgentRepository` 中的 `agent.daily-limit`，原有行锁语义不变。
- **会话撤销**：`ClosetAccountService.setEnabled/resetPassword/changeRole/revokeSessions` 返回删除的会话数；CLI 走同一路径，因此命令行禁用用户也会立即踢下线。
- **验证脚本**：`scripts/manage-curl.sh METHOD PATH [JSON]` 只依赖 openssl、python3、curl。
