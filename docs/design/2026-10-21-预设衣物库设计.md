# 预设衣物库设计

> 状态：**P0~P2 已实施**（2026-10-21），P3 补全覆盖由管理员持续进行。来源：总设计 10.1 后续池“预设衣物库”，[推荐对象设计](2026-10-20-推荐对象：年龄感与着装取向设计.md)第十二节（#61 遗留问题）。
> 已由用户确认的：预设衣物复制进用户衣柜并标识“预设”；参与正式推荐（靠曝光均衡轮换）；规模约 300 件，以管理员账号 yaopinxin 现有约 250 件为底，再补风格方向缺的品类，之后持续补全。

## 一、问题

1. **新用户冷启动**：注册后衣柜一片空白，推荐、今日灵感、组合台、OOTD 都用不起来，“用下去的心都没了”。
2. **覆盖不全导致推荐失真**（#61）：衣柜只有一类人的衣服时，换成别的年龄或性别设置，引擎再准也挑不出合适的组合。
3. **风格方向缺衣物**：用户选了“户外机能”“巴恩风”，衣柜里却没有对应单品，偏好只能落空。

## 二、目标与非目标

**目标**

- 维护一份系统级的预设衣物库：常见基础款，按性别、风格方向、季节都有覆盖。
- 新用户可以在引导里勾选“我有类似的”，几十秒建一个起步衣柜。之后随时把预设换成自己的实拍。
- 老用户也能从预设库补衣物（例如“我其实有一件风衣，只是没拍”）。
- 预设衣物在衣柜、推荐卡片、组合台上都有明确标识，不会被当成用户自己拍的。

**非目标**

- 不做商品推荐、购买链接或导流。
- 不自动往用户衣柜里塞衣物：一律由用户勾选。
- 本期不做跨用户的预设库审核流程（只有管理员维护）。

## 三、数据来源与隐私

- **来源**：从指定账号（默认 yaopinxin）的已入柜衣物导出，由管理员挑选后进入预设库；之后管理员可继续往库里加。
- **只带走衣物本身**：品类、颜色、图案、版型、季节、风格、适穿性别、长度、门襟、纹理、展示图。
- **不带走**：穿着记录、反馈、收藏、搭配、模特与 OOTD、原图（只保留处理后的展示图），以及可能含个人信息的字段（可见文字、尺码、洗护、品牌）。
- **图片**：直接使用现有的展示图（大部分已经抠图处理），本期不区分图片来源（用户 2026-10-21 确认）。

## 四、存储方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 每个用户复制一份图片 | 导入时把展示图文件复制到用户自己的处理任务下 | 现有图片访问和权限逻辑完全不用改 | 300 件 × 用户数的重复文件，加上缩略图，占用成倍增长 |
| **B. 图片共享、衣物资料复制（推荐）** | 预设库的图片放在系统账号下，只存一份；导入时复制衣物资料（garment 行），`display_asset_id` 指向共享图片；图片访问规则增加“预设图片对所有登录用户只读” | 图片只存一份；资料仍是用户自己的，可以随便改 | 要改图片访问校验；用户换图时不能改共享图片，要先复制再改 |

推荐 **B**：
- 衣物表新增 `preset_id`（来自哪件预设，可空）。`source_origin` 新增取值 `PRESET`。
- 用户改资料：直接改自己的行（和现在一样，写 overrides），不影响预设库和其他用户。
- 用户换图或重新处理图片：走现有流程，在用户自己的任务下生成新图，`display_asset_id` 指向新图；共享图片不动。换成实拍后，`source_origin` 改为 `USER_UPLOAD`，预设标识随之消失，`preset_id` 保留以便统计。

## 五、预设库本身

- 新表 `preset_garment`：id、来源衣物 id、展示图 asset id、衣物资料快照（JSON，按第三节过滤）、覆盖标签（性别、风格方向、季节，便于引导筛选）、状态（草稿、已上架、下架）、排序、创建与更新时间。
- 管理员操作（先放在鱼搭内管理页，之后补 `/api/manage/v1`，同步 yaml）：
  1. **从账号导入草稿**：选择账号（默认 yaopinxin），列出已入柜衣物，勾选后生成草稿；图片复制到系统账号下，只复制一次。
  2. **逐件核对**：资料、标签、图片来源（自拍或商品截图），然后上架。
  3. **下架**：不再出现在引导里；已经导入用户衣柜的副本不受影响。
- 覆盖统计：按“性别 × 品类大类 × 风格方向”统计数量，提示哪里缺（例如“男款下装 3 件”“户外机能 0 件”），帮助补到约 300 件。

## 六、用户侧

### 6.1 新用户引导

- **触发**：首次登录且衣柜为空（已有衣物不打扰）。
- **流程**：
  1. 选性别（沿用个人资料）、风格年龄感、最多 3 个常穿风格。三项都可以跳过，并且会直接写进“推荐给谁”和“常穿风格”设置。
  2. 按上一步的选择列出推荐的预设衣物，按上装、下装、外套、鞋分组，默认不勾选。用户勾“我有类似的”。
  3. 确认后导入，提示“这些是示意图，之后可以换成你自己的照片”。
- 可以跳过整个引导，之后在衣柜页“从常见单品添加”再进入。

### 6.2 标识

- 衣柜卡片、衣物详情、推荐卡片、组合台：在角标上标“预设”（灰色小标签，Ant Design Vue `a-tag`）。
- 衣物详情：在显眼位置放“换成我的照片”按钮，进入现有的上传与处理流程，并保留已有资料。
- OOTD 生图：预设衣物可以参与，但卡片上提示“示意图，效果仅供参考”。

### 6.3 推荐

- 预设衣物和自己的衣物同等参与推荐，靠曝光均衡轮换，不额外加分也不额外扣分。
- 推荐卡片里含预设衣物时，用户可见的 `notes` 里写一句“含 N 件预设衣物（示意图）”。
- 规模控制：用户导入的预设一般不超过几十件，不需要额外的性能处理。

## 九、P0 + P1 后端实施记录（2026-10-21）

本次仅在 `feat/preset-backend` 实施后端，前端由独立仓库接入。识图提示词、审美/人群规则与风格画像 JSON 均未修改。

### 存储与隐私

- V32 新增 `preset_garment`，保留来源衣物编号和账号以便管理员追溯；额外保存名称。来源编号不设外键，以免来源衣物删除导致预设失效。`garment.preset_id` 关联预设；`(owner_username,preset_id)` 唯一约束和账号行锁共同防止并发重复导入，包括已有副本在回收站或已换图的情况。
- 共享图命名空间固定为 `PresetOwner.USERNAME = __preset__`。它不是账号，不可注册、管理员创建、CLI 创建或登录；服务校验、认证提供器和数据库大小写不敏感 CHECK 三层约束。
- 管理员导入只读取来源账号 ACTIVE 衣物的有效字段，按 RecognitionSchema 白名单保存值，剔除 `visibleText/size/careInstructions/brand/materialComposition`。不复制识图 evidence、target、原始响应或任何穿着、反馈、收藏、搭配、人物记录。名称按确认需求复制，管理员上架前应核对。
- 只把当前展示图的字节复制进独立的 SUCCEEDED 系统任务，`garment_id` 为空。`preset_image.sha256` 唯一索引跨来源衣物去重；全局导入锁避免并发写出两份。同一 SHA 也只保留一份图片风格快照，不保留原账号的风格依据。
- PNG 共享副本统一用 `input.png`，JPEG 用 `original.jpg`，兼容已有文件 GET 和缩略图路由（来源可能是 `base-cutout.png`）。事务回滚时删除本次新写的副本；已存在的共享图不写入、不删除。
- 同一来源重复导入会更新并恢复为 DRAFT；已 LISTED 的快照保持不动。重新导入不更新任何用户副本。

### 接口与字段

| 方法 | 路径 | 行为 |
|---|---|---|
| POST | `/api/admin/presets/import` | `{username, garmentIds?}`；未给 garmentIds 时导入该账号全部 ACTIVE，空列表不导入；显式指定非 ACTIVE/非来源账号衣物报 400；返回管理员预设数组 |
| GET | `/api/admin/presets?status=` | 全部或按 DRAFT/LISTED/UNLISTED 过滤，按 sort、id 排序 |
| PATCH | `/api/admin/presets/{id}` | `{status?, gender?, styles?, seasons?, sort?}`；逐项更新，不传则保留 |
| GET | `/api/admin/presets/coverage` | 仅统计 LISTED；返回完整性别 × 六品类组 × 风格方向网格，每格含 count、missing，零格也返回 |
| GET | `/api/presets?gender=&styles=&season=` | 仅 LISTED，返回 id、displayAssetId、displayUrl、name、fields、gender、styles、seasons、alreadyImported；不返回来源账号/编号 |
| POST | `/api/presets/import` | `{ids:[UUID...]}`，每次 1–100 项；整批事务，返回 `{garmentIds:[新衣物ID], skipped:[已导入预设ID]}`；请求内重复编号合并 |
| POST | `/api/closet/garments/{id}/photo` | Multipart `file` + `workflow`，沿用衣物上传的 UploadOptions 和处理模式，必需 Idempotency-Key；上传到原衣物，不创建另一件衣物 |

管理员接口同时受现有 `/api/admin/**` 安全链与服务角色检查保护，普通用户返回 403。用户接口需要登录。

性别标签取 `男款/女款/中性/未标注`，gender 筛选按标签精确匹配；seasons 取 `春/夏/秋/冬`。styles 接受现有 24 个画像的风格词及九个风格方向别名，统一到画像 label；另保留 `都市通勤/潮流运动`（`通勤/运动` 可作别名）。覆盖网格包含这两项和“未标注”，不把画像压成七个粗标签。styles 可用逗号分隔或重复参数，多个方向取并集。覆盖按 OutfitRules 的固定顺序推导，INNER 归 top、OVERALL 归 one-piece，配件角色归 accessory；OTHER 不冒充配件。未标注项另有格子，管理员应核对无法分类的品类。

管理员核对的 gender、seasons 同步进预设字段快照，影响以后导入的副本；styles 是覆盖与筛选标签，保留衣物原有的风格字段，不自动改写。管理员不能通过这些接口操作用户副本。

### 用户副本、图片权限与推荐

- 导入创建新 ACTIVE 衣物，`source_origin=PRESET`，source/display 同指共享 asset；资料只存进新行的 `overrides_json`，作为管理员核对后可正常编辑的资料。automatic 为空，无原账号的识别任务/evidence。列表与详情现有 `sourceOrigin` 可用于“预设”标签，推荐 `OutfitView.garments` 增加 `preset` 布尔值。
- 同账号已有任意状态的同一 preset_id 时跳过，不自动恢复回收站衣物；用户可先去回收站恢复。当前仓库没有衣物总数额度；现有额度针对模型调用，纯资料导入不扣 AI 额度。后续照片处理仍走已有队列、模型授权和额度限制。
- 仅图片文件 GET 使用 `workflowRead`；普通私有任务仍只能由所属账号读。共享文件及其 `?w=` 缩略图对已登录用户只读。任务 JSON、review、cancel、continue、幂等键复用、资产选择等继续用严格的 workflow/asset 所属校验；管理员也没有共享任务写权限。
- 换图复用现有上传处理流程。上传原图改为用户任务的 source_asset；手动选图、确认入柜或自动采纳处理输出都会把 PRESET 改为 USER_UPLOAD，保留 preset_id、用户资料和历史。重新处理共享图也只生成用户任务的新文件；不修改共享文件。
- 移入回收站只改用户衣物状态。仓库尚无衣物物理清除接口；测试直接 DELETE 用户 garment 行，验证共享系统任务、文件、其他用户副本和预设仍在。共享图没有用户 garment_id 关联，不能被按用户衣物任务清理的逻辑带走；今后若增加清除器必须保持此约束。
- 推荐评分与召回完全沿用现有路径；没有预设专属加分、扣分或排除。打卡和闲置激活使用同一 garment ID 路径，无来源过滤。推荐展示及助手卡片/临时搭台 notes 增加“含 N 件预设衣物（示意图）”，按当前页主体衣物 ID 去重计数；不放进 limits、评分依据或发给模型的精简结果。

### 派生数据

- 色板：`GarmentColors.pendingOwners` 自动发现新 ACTIVE 行，ColorIndexHandler 在 30 秒扫描轮次补算；从共享展示图读取，保存为各用户衣物自己的 garment_color。
- 描述向量：`GarmentEmbeddings` 按衣物 ID/revision 发现缺失，SemanticIndexHandler 在本地模型可用时生成；只使用过滤后的新副本资料，不复用原账号卡片或 evidence。
- 图像向量：ImageIndexHandler 的 ActivityProbe 发现 ACTIVE 数量/更新时间变化；按新衣物 ID 和共享 display asset 建立各自向量。本地图像模型未安装时不调度、不自动下载，待安装后扫描补齐。
- 图片指纹：VisualIndexHandler 同样自动发现新增行并补算；重复检查沿用普通衣物路径。
- 图片画风：管理员导入时从 ImageStyles 的现有规则得到源展示图风格，仅保存风格枚举。用户导入时写入绑定共享展示图的 MODEL 风格快照和固定说明，无新增视觉模型调用；之后换图按原有失效/推导逻辑处理。
- 缩略图/WebP：继续使用 StoredMedia + ImageVariants，按共享文件 key、版本、宽度和格式缓存。所有用户 URL 相同，复用缓存；原文件保持不变。
