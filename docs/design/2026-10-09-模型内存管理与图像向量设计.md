# 模型内存管理与图像向量设计（2026-10-09）

**状态：第一部分（内存管理：抠图模型闲置卸载、运维看实际内存）已实施，分支 `feat/model-memory`；第二部分（本地图像向量模型）待你确认第六节的决定后实施。** 接续 [相似衣物提示与以图搜图设计](2026-10-09-相似衣物提示与以图搜图设计.md) 的第三期。决策 G1~G9。

## 一、背景：4c4g，内存是瓶颈

线上服务器 4 核 4G，CPU 基本空闲，内存约 60%（约 2.4G）。已装两个模型：

| 模型 | 文件 | 加载后约占（估算，以 RSS 实测为准） | 实际使用频率 |
|---|---|---|---|
| U²-Net 抠图 | 176MB | 200~400MB | 只在录入衣物时 |
| bge-small 文本向量 | 95MB | 100~150MB | 每次搜索、推荐 |

模型会话占用的是 **Java 堆外内存**：JVM 堆的数字里看不到，只能看进程常驻内存（RSS）。Docker 镜像目前没有设置 `-Xmx`，JVM 默认最多用容器内存的 1/4 作堆。

## 二、原则

1. **按使用频率决定是否常驻**（G1）：每次请求都要用的常驻（文本向量）；偶尔用的“用时加载、闲置卸载”（抠图、图像向量）。
2. **宁可降级，不可被杀**（G2）：内存紧张时关闭可选能力（回到零模型的相似提示和以图搜图），不能让 Linux 因内存不足杀掉整个服务。
3. **后台计算让路**（G3）：给衣物补算向量这类后台任务单线程、低优先级，不和用户请求抢资源。
4. **看得见**（G4）：运维状态里能看到进程实际内存、各模型是否已加载、卸载过几次。

## 三、已实施：抠图模型闲置卸载与内存可见

- 抠图会话闲置 `CLOSET_SEGMENTATION_IDLE_UNLOAD`（默认 10 分钟）后释放，下次录入时自动重新加载（多等约 1 秒）。设为 `0` 则常驻。
- **推理进行中绝不卸载**：每次推理持有读锁，卸载只在拿到写锁时进行，拿不到就等下一轮。
- 后台检查线程每 1~60 秒看一次（随闲置时长缩放），只做一次时间比较，几乎不占资源。
- 管理接口 `/ops/status` 新增：`jvm.processRssBytes`（进程实际常驻内存）、`systemMemoryTotalBytes` / `systemMemoryFreeBytes`、`models.segmentation.idleUnloadMinutes` 与 `unloads`（卸载次数）。
- 测试用一个 161 字节、输入输出形状与 U²-Net 相同的替身 ONNX 模型，在真实 ONNX Runtime 上验证：加载 → 闲置卸载 → 再用时重新加载；推理中不卸载；设为 0 时常驻。

**效果**：服务器大部分时间不在录入衣物，抠图模型占的几百 MB 会被释放出来，正好给图像向量模型腾出空间。

## 四、图像向量：引入后能做到什么

### 4.1 能明显变好的

| 场景 | 现在（零模型） | 加图像向量后 |
|---|---|---|
| 同一件衣服换角度、换光线重拍 | 认不出（只比颜色轮廓） | 能认出，可提示“可能重复” |
| 平铺照 vs 穿在身上的照片 | 认不出 | 多数能认出（效果取决于模型和遮挡程度） |
| 以图搜图：拿商品图/别人的穿搭截图找“我有没有类似的” | 只能按颜色、轮廓 | 能按款式、图案、材质感找（条纹 vs 格纹、针织 vs 牛仔、廓形） |
| 相似的衣物 | 颜色轮廓相近 | 加上“看起来是同一类款式”，排序更符合直觉 |
| 用文字找图片（只在选中文图文模型时） | 只能搜识图得到的文字字段 | “带小熊图案的白T”这类识图没写进字段的细节也能搜到 |

### 4.2 做不到或不保证的

- **完全相同款式的不同件**：两件同款黑 T 恤（比如买了两件）看起来就是一样的，只能靠“不是重复”标记区分。
- **严重遮挡、多件同框**：一张图里好几件衣服时需要先选定要找哪一件（本地抠图会取最显著的那件）。
- **品牌、尺码、材质成分**：图像向量不认这些。
- **小模型的精度上限**：4c4g 只适合小模型，细粒度区分（两件相近的条纹衫）不如大模型。具体能做到多少，要用你的真实衣柜做评估后给数字（见 4.3），现在不承诺。

### 4.3 怎么验证效果（上线前）

用 50~100 件真实衣物，人工标注三类对：同一件不同照片、相似款、不同款。指标：

| 指标 | 含义 |
|---|---|
| 同件召回 | 同一件的另一张照片排在前 5 的比例 |
| 重复误报率 | 被判“可能重复”但其实不是同一件的比例 |
| 搜图前 5 命中 | 以图搜图时，人工认为“像”的结果在前 5 的比例 |
| 单张编码耗时、常驻内存、补算 1000 件的时间 | 在 4c4g 上实测 |

同时对比“零模型”和“加图像向量”两版，效果明显好才默认开启。

## 五、图像向量的实现方案（待确认后实施）

| 环节 | 方案 |
|---|---|
| 模型文件 | 放 `./models/`，`scripts/install-models.sh` 加一行；固定版本、校验 SHA-256；服务不联网下载 |
| 加载 | 与文本向量相同的“后装免重启”；与抠图相同的“用时加载、闲置卸载” |
| 编码对象 | 衣物展示图（抠图后），绑定展示图版本，换图重算 |
| 后台补算 | `IMAGE_INDEX` 任务单线程、低优先级、每批 50 件，补完即卸载模型 |
| 存储 | `garment_image_embedding(garment_id, display_asset_id, model_version, vector)`，按用户读取并短期缓存 |
| 相似度 | 在现有五项上加 `image` 一项并给最高权重（初定 0.35，其余按比例缩小）；“可能重复”允许由“图像向量很高 + 颜色接近 + 字段不矛盾”判出（不再要求同一张图） |
| 以图搜图 | 查询图本地抠图后编码，与衣柜向量比；没有模型时自动回到现在的零模型版 |
| 内存保护 | 加载前检查系统可用内存，低于阈值（初定 600MB）就不加载、本次走零模型版，并在运维状态里报 `IMAGE_MODEL_SKIPPED_LOW_MEMORY` |

## 六、需要你决定的

| # | 问题 | 选项 | 我的建议 |
|---|---|---|---|
| 1 | 要不要“用文字找图片” | 要（选中文图文模型，多一个文本塔，内存多约 100~200MB，可同样闲置卸载） / 不要（只要图像塔，最省） | 先不要；以图搜图和重复检测只需要图像塔。以后需要再加 |
| 2 | 模型档位 | 小（MobileCLIP 一类，约 50~100MB，几十毫秒/张） / 中（ViT-B int8，约 100MB+，几百毫秒/张） / 大（ViT-B fp32，约 350MB+） | 小档，4c4g 下最稳；评估效果不够再试中档 int8 |
| 3 | 图像相似度要不要进推荐 | 只用于相似提示和以图搜图 / 也用于推荐（如“换一件”优先给款式相近的、多样化时避开几乎一样的两件） | 先只用于相似和搜图；推荐保持现有白盒规则，稳定后再说 |
| 4 | 图像向量判出的“可能重复”是否和现在一样醒目提示 | 一样提示 / 只在“整理衣柜”里列出，不在详情页醒目提示 | 初期只在“整理衣柜”列出，误报率评估合格后再醒目提示 |
| 5 | 评估数据谁来准备 | 你从自己的衣柜挑 50~100 件、我出标注表 / 我用公开的商品图（需核实许可） | 用你的真实衣柜，最能反映实际效果 |
| 6 | 内存紧张时的策略 | 跳过加载走零模型版（默认） / 先卸载抠图再加载图像模型 / 直接报错 | 跳过加载走零模型版，并在运维状态里提示 |
| 7 | 后台补算时间 | 入柜后立刻（几十秒内） / 只在夜间空闲时段 | 立刻，但单线程低优先级；CPU 空闲，没必要等夜间 |
| 8 | 模型的许可证 | 只用允许商用的 / 研究用途也可 | 只用允许商用的；候选模型的许可证我在实施前逐一核实并写进 `models/README.md` |
| 9 | JVM 堆上限 | 不设（默认容器内存的 1/4） / 显式设 `-Xmx`（如 1g） | 显式设 1g，给模型的堆外内存留出确定的空间；部署时一起改 |

## 七、内存预算（4G，估算，部署后用 RSS 校准）

| 项 | 现在 | 加小图像模型后（抠图与图像模型闲置时） | 加小图像模型后（录入 + 补算同时进行的峰值） |
|---|---|---|---|
| 系统、Docker、Agent 运行时 | 约 0.6~0.8G | 同左 | 同左 |
| JVM 堆（设 1g 上限） | ≤1G | ≤1G | ≤1G |
| 文本向量 | 约 0.15G | 约 0.15G | 约 0.15G |
| 抠图 | 约 0.2~0.4G（常驻） | **0**（闲置已卸载） | 约 0.2~0.4G |
| 图像向量（小档） | — | **0**（闲置已卸载） | 约 0.1~0.2G |
| 合计 | 约 2.0~2.4G | 约 1.8~2.0G | 约 2.1~2.8G |

结论：先上线抠图闲置卸载，平时内存会比现在低；加小档图像模型后，峰值也低于 4G 的 70%。
